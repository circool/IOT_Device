## 1. Назначение

Транспортная абстракция — это **самовосстанавливающаяся сущность**, которая обеспечивает постоянный канал связи между устройством и внешним миром (системы умного дома, пользователь). Транспорт является **единой точкой входа** для всех внешних взаимодействий.

**Транспорт объединяет:**
- **Среду передачи** (WiFi STA, Zigbee, Thread) — физический канал для постоянной связи
- **Прикладные протоколы** (HTTP, MQTT, ZCL, Matter) — способ обмена данными

**Транспорт управляет:**
- Параметрами канала связи (WiFi SSID/пароль, MQTT брокер/порт/логин/пароль)

**Транспорт НЕ управляет:**
- Бизнес-параметрами устройства (пороги, таймеры, режимы, скорость)
- Эти параметры — ответственность DeviceController

**Транспорт владеет ресурсами:**
- WiFi (управляет режимами STA/AP)
- HTTP-сервер
- MQTT-клиент
- BLE-сервер (используется только в режиме настройки)

**Границы:**
- Транспорт не содержит бизнес-логику устройства
- Транспорт не принимает решений о том, что делать с конфигурацией (только передаёт оркестратору)
- Транспорт не знает, откуда пришла команда (Web/MQTT/Zigbee/Matter)

## 2. Принципы

| Принцип | Описание |
|---------|----------|
| **Единый интерфейс** | Все транспорты реализуют структуру `Transport` с одинаковыми методами |
| **Самодостаточность** | Транспорт сам управляет своей средой и процессом настройки |
| **Среда и протоколы разделены** | Транспорт управляет средой отдельно от протоколов |
| **Самовосстановление** | Транспорт самостоятельно восстанавливает связь при потере |
| **Компиляция** | Выбор транспорта — через `#if` в `transport_factory.h` |
| **Независимость** | Транспорт не знает о бизнес-логике, только о командах и публикациях |
| **Единая точка входа** | Все внешние команды поступают через транспорт |

└─────────────────────────────────────────────────────────────────────────────┘
                                    ▲
                                    │ Единый интерфейс Transport
                                    ▼
┌─────────────────────────────────────────────────────────────────────────────┐

## 4. Режимы работы транспорта

Транспорт работает в одном из двух режимов. Переключение между режимами — **полностью автоматическое**, без участия оркестратора.

| Компонент | Обычный режим (STA) | Режим настройки (AP) |
|-----------|---------------------|---------------------|
| **WiFi** | STA (подключён к роутеру) | AP (точка доступа) |
| **HTTP-сервер** | Страница состояния | Страница ввода данных |
| **MQTT-клиент** | ✅ Работает | ❌ Не работает |
| **BLE-сервер** | ❌ Не работает | ✅ Работает |

### 4.1. Обычный режим (STA)

- Устройство подключено к WiFi-роутеру
- HTTP-сервер отображает страницу состояния
- MQTT-клиент активен
- BLE-сервер выключен
- Транспорт принимает команды и публикует состояние

### 4.2. Режим настройки (AP)

- Устройство создаёт WiFi-точку доступа
- HTTP-сервер отображает страницу ввода учётных данных
- MQTT-клиент выключен
- BLE-сервер активен (ESP BLE Provisioning)
- Транспорт собирает данные от пользователя

### 4.3. Переключение между режимами

```
Обычный режим (STA)
    │
    │ Потеря связи / нет конфигурации
    ▼
Режим настройки (AP)
    │
    │ Получены и проверены данные
    ▼
Обычный режим (STA)
```

**Переключение выполняется транспортом автоматически**:
1. При старте: если нет конфигурации → режим настройки
2. В процессе работы: потеря связи → попытки переподключения → если не удаётся → режим настройки
3. После получения данных: проверка → успех → обычный режим

## 5. Структура Transport

### 5.1. Интерфейс транспортной абстракции

```cpp
typedef struct Transport {
    // ===== УПРАВЛЕНИЕ =====
    bool (*begin)(const TransportConfig* config);
    void (*update)();
    
    // ===== ПУБЛИКАЦИЯ (устройство → внешний мир) =====
    void (*publishState)(const DeviceState* state);
    void (*publishSettings)(const DeviceConfig* settings);
    
    // ===== КОЛБЭКИ (внешний мир → устройство) =====
    void (*onCommand)(TransportCommandCallback callback);
    void (*onConfigUpdate)(TransportConfigCallback callback);
} Transport;
```

### 5.2. Стандарт интерфейсов прикладных протоколов

Все прикладные протоколы (HTTP, MQTT) должны реализовывать единый набор методов для взаимодействия с WiFi-транспортом:

| Метод | Назначение |
|-------|------------|
| `init()` | Инициализация протокола (выделение ресурсов, регистрация) |
| `begin(config)` | Запуск протокола с переданной конфигурацией |
| `update()` | Периодическая обработка (вызывается в loop()) |
| `set_mode(mode)` | Переключение режима работы протокола |
| `update_state(state)` | Получение нового состояния устройства |
| `update_settings(settings)` | Получение новых настроек устройства |

**Принципы:**
1. **Единообразие** — все протоколы используют одинаковые имена методов для одинаковых действий.
2. **Минимализм** — интерфейс должен содержать только необходимые методы.
3. **Предсказуемость** — разработчик, зная один протокол, легко понимает другой.

## 6. Структуры данных

### 6.1. TransportConfig — параметры канала связи

```cpp
typedef struct {
    // ===== ОБЩИЕ ПАРАМЕТРЫ =====
    char deviceId[32];
    
    // ===== WiFi (только если USE_WIFI == 1) =====
    #ifdef USE_WIFI
        char wifiSsid[32];
        char wifiPassword[64];
    #endif
    
    // ===== MQTT (только если USE_MQTT == 1) =====
    #ifdef USE_MQTT
        char mqttBroker[64];
        uint16_t mqttPort;
        char mqttUser[32];
        char mqttPassword[64];
        char mqttClientId[24];
    #endif
    
    // ===== Zigbee (только если USE_ZIGBEE == 1) =====
    #ifdef USE_ZIGBEE
        uint16_t zigbeePanId;
        uint8_t zigbeeChannel;
        char zigbeeNetworkKey[32];
    #endif
    
    // ===== Thread (только если USE_THREAD == 1) =====
    #if USE_THREAD == 1
        char threadNetworkName[32];
        char threadNetworkKey[32];
        uint16_t threadPanId;
        uint8_t threadChannel;
    #endif
} TransportConfig;
```

### 6.2. DeviceConfig — бизнес-настройки устройства (сохраняются в EEPROM)

```cpp
typedef struct {
    bool sensorMode;  // TRUE = SENSOR, FALSE = MANUAL
    bool adaptiveMode;        // TRUE = адаптивный режим включён
    float lowTemp;
    float highTemp;
    float lowHum;
    float highHum;
    uint32_t delaySec;
    uint32_t maxOnTime;
    uint8_t bootState;        // 0 = OFF, 1 = ON
} DeviceConfig;
```

### 6.3. DeviceState — оперативное состояние устройства

```cpp
ypedef struct {
    bool is_on;              // Актуатор включён
    uint8_t speed;           // 0-100%
    float temperature;
    float humidity;
    bool sensorMode;        // TRUE = SENSOR, FALSE = MANUAL
    bool adaptiveMode;    // TRUE = адаптивный режим активен
    uint32_t delay_remain;   // Остаток таймера задержки (сек)
    uint32_t max_on_remain;  // Остаток аварийного таймера (сек)
    const char* reset_reason; // Причина последней перезагрузки (NULL = нет причин)
} DeviceState;
```

## 7. Типы колбэков

```cpp
// ===== КОМАНДЫ =====
typedef enum {
    // Команды управления (оперативные)
    CMD_STATE,                // bool — включить/выключить
    CMD_SPEED,                // int — скорость 0-100%
    
    // Настройки (сохраняются в EEPROM)
    CMD_SET_SENSOR_CONTROL_MODE,  // bool — SENSOR/MANUAL
    CMD_SET_ADAPTIVE_MODE,        // bool — адаптивный режим
    CMD_SET_LOW_TEMP,             // float — нижний порог температуры
    CMD_SET_HIGH_TEMP,            // float — верхний порог температуры
    CMD_SET_LOW_HUM,              // float — нижний порог влажности
    CMD_SET_HIGH_HUM,             // float — верхний порог влажности
    CMD_SET_DELAY_SECONDS,        // uint32_t — задержка включения
    CMD_SET_MAX_ON_TIME,          // uint32_t — аварийное отключение
    CMD_SET_BOOT_STATE,           // bool — состояние при старте
} TransportCommand;

typedef struct {
    TransportCommand type;
    union {
        bool boolVal;      // Для типов bool
        int intVal;        // Для скорости (0-100%)
        float floatVal;    // Для температуры и влажности
        uint32_t u32Val;   // Для таймеров
    } value;
} TransportCommandData;

typedef void (*TransportCommandCallback)(TransportCommand cmd, const TransportCommandData* data);

// ===== ИЗМЕНЕНИЕ ПАРАМЕТРОВ СВЯЗИ =====
typedef void (*TransportConfigCallback)(const TransportConfig* config);
```

## 8. Жизненный цикл транспорта

```
┌─────────────────────────────────────────────────────────────────────────────┐
│ 1. begin(config)                                                           │
│    • Проверить конфигурацию канала связи                                    │
│    • Если есть данные → переключиться в обычный режим (STA)                │
│    • Если нет данных → переключиться в режим настройки (AP)                │
└─────────────────────────────────────────────────────────────────────────────┘
                                    │
                                    ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│ 2. update() — вызывается в loop()                                          │
│                                                                             │
│    А. Если режим настройки активен:                                        │
│       • Обработать HTTP-запросы                                             │
│       • Обработать BLE-события (если есть)                                  │
│       • Если данные получены → проверить их                                 │
│       • Если валидны → применить, переключиться в обычный режим            │
│       • Если невалидны → продолжить режим настройки                        │
│                                                                             │
│    Б. Если обычный режим активен:                                          │
│       • Поддерживать WiFi-соединение                                        │
│       • Поддерживать MQTT-соединение                                       │
│       • Обрабатывать входящие команды через onCommand()                     │
│       • Публиковать состояние через publishState()                          │
│       • При потере связи → попытки переподключения                          │
│       • При невозможности переподключиться → переключиться в режим настройки│
└─────────────────────────────────────────────────────────────────────────────┘
```

## 9. Колбэк оркестратору

Транспорт уведомляет оркестратора через два колбэка:

### 9.1. onCommand — команды и настройки устройства

Вызывается при любой команде от пользователя или системы:

```cpp
// Команда управления
_onCommand(CMD_STATE, &data);  // data.boolVal = true

// Изменение бизнес-настройки
_onCommand(CMD_SET_LOW_TEMP, &data);  // data.floatVal = 26.0
```

**Что передаётся:**
- Команды управления (включить, изменить скорость)
- Изменение бизнес-настроек (пороги, таймеры, режимы)

**Что делает оркестратор:**
- Определяет тип команды по `type`
- Вызывает соответствующий метод DeviceController

### 9.2. onConfigUpdate — параметры канала связи

Вызывается при изменении параметров связи (WiFi, MQTT, Zigbee, Thread):

```cpp
// Изменение параметров связи
_onConfigUpdate(&_transportConfig);
```

**Что передаётся:**
- WiFi SSID и пароль
- MQTT брокер, порт, логин, пароль
- Client ID
- Zigbee/Thread параметры (если используются)

**Что делает оркестратор:**
- Сохраняет параметры в ConfigManager

## 10. Управление флагами состояния

Транспорт обновляет следующие флаги в `TransportState`

### 10.1. Флаги состояния

| Флаг | Кто пишет | Когда |
|------|-----------|-------|
| `link_ok` | Конкретная реализация транспорта | При изменении статуса среды (WiFi/Zigbee/Thread) |
| `gateway_ok` | Прикладной протокол / стек | При изменении статуса сервиса (MQTT/Coordinator/Border Router) |
| `setup_mode` | Конкретная реализация транспорта | При переключении в режим настройки/обратно |
| `link_quality` | Конкретная реализация транспорта | При изменении уровня сигнала |

### 10.2. Разделение ответственности

| Компонент | Устанавливает |
|-----------|---------------|
| **WiFi-транспорт** | `link_ok`, `link_quality`, `setup_mode` |
| **MQTT-протокол** | `gateway_ok` (если MQTT включён) |
| **Zigbee-транспорт** | `link_ok`, `gateway_ok`, `setup_mode` |
| **Thread-транспорт** | `link_ok`, `gateway_ok`, `setup_mode` |

### 10.3. Принципы

1. **Каждый компонент устанавливает только свои флаги**
   - WiFi-транспорт не знает о MQTT
   - MQTT-протокол не знает о WiFi

2. **HTTP не управляет `gateway_ok`**
   - HTTP — пассивный сервер, а не внешний сервис
   - Его работа полностью зависит от `link_ok`

```cpp
// // TransportState должен реализовать следующие флаги
typedef struct {
    // ===== ОБЩИЕ ФЛАГИ (для всех транспортов) =====
    bool link_ok;          // Среда есть (WiFi/Zigbee/Thread)
    bool gateway_ok;       // Сервис доступен (MQTT/Coordinator/Border Router)
    bool setup_mode;       // Идёт настройка
    
    #ifdef USE_WIFI
        int8_t link_quality;  // RSSI в dBm (-100..0), только для WiFi
    #endif
    
} DeviceState;
```
### 10.4. Диагностический флаг reset_reason

`reset_reason` — диагностический флаг, аналогичный CHECK ENGINE в автомобиле.

**Ответственность:**
- **DeviceController** — устанавливает и сбрасывает флаг (по таймеру или после N штатных перезагрузок).
- **Транспорт** — только публикует значение.

## 11. Реализации транспортов

### 11.1. WiFi-транспорт

**Среда:** WiFi (STA/AP)

**Протоколы:**
- HTTP (всегда)
- MQTT (опционально)

**Режимы:**
- Обычный: STA + HTTP (состояние) + MQTT
- Настройки: AP + HTTP (ввод данных) + BLE

**Особенности:**
- Поддерживает BLE для режима настройки (ESP32)
- HTTP-сервер работает в обоих режимах

**Документация:**
- `TRANSPORT_WIFI.md` — реализация WiFi-транспорта
- `TRANSPORT_HTTP.md` — HTTP-протокол
- `TRANSPORT_MQTT.md` — MQTT-протокол
- `TRANSPORT_BLE.md` — BLE-сервер для режима настройки

### 11.2. Zigbee-транспорт

**Среда:** Zigbee

**Протоколы:** ZCL

**Режимы:**
- Обычный: подключён к Zigbee-сети
- Настройки: автоматическое присоединение к координатору (Permit Join)

**Статус:** Заглушка (реализация отсутствует)

**Документация:** `TRANSPORT_ZIGBEE.md`

### 11.3. Thread-транспорт

**Среда:** Thread

**Протоколы:** Matter

**Статус:** Не реализован

**Документация:** `TRANSPORT_MATTER.md`

## 13. Фабрика транспортов

Фабрика выбирает реализацию транспорта **на этапе компиляции** на основе флагов `USE_*`.

```cpp
// transport_factory.h
#ifndef TRANSPORT_FACTORY_H
#define TRANSPORT_FACTORY_H

#include "settings.h"
#include "transport.h"

// Подключаем реализации в зависимости от флагов
#ifdef USE_WIFI
    #include "transport_wifi.h"
#elif USE_ZIGBEE == 1
    #include "transport_zigbee.h"
#elif USE_THREAD == 1
    #include "transport_thread.h"
#endif

/**
 * @brief Создать транспорт в зависимости от USE_* флагов
 * @return Указатель на структуру Transport или nullptr
 */
inline Transport* createTransport() {
    #ifdef USE_WIFI
        return getWiFiTransport();
    #elif USE_ZIGBEE == 1
        return getZigbeeTransport();
    #elif USE_THREAD == 1
        return getThreadTransport();
    #else
        #error "No transport selected! Set USE_WIFI, USE_ZIGBEE or USE_THREAD"
        return nullptr;
    #endif
}

#endif  // TRANSPORT_FACTORY_H
```

**Использование в оркестраторе:**

```cpp
// main.cpp
#include "transport_factory.h"

void setup() {
    // ...
    g_transport = createTransport();
    if (!g_transport) {
        XLOG_ERROR(CAT_MAIN, "Failed to create transport!");
        return;
    }
    // Оркестратор работает с единым интерфейсом Transport
    g_transport->begin(&config);
    g_transport->onCommand(onCommand);
    g_transport->onConfigUpdate(onConfigUpdate);
}
```

## 14. Компиляция отдельных блоков

Транспортный слой собирается модульно. Включение/исключение компонентов управляется **внутренними флагами** (`USE_*`), которые вычисляются в `settings.h` на основе пользовательских настроек и аппаратной совместимости платформы.

В коде транспорта используются только внутренние флаги `USE_*`:

| Внутренний флаг | Назначение |
|-----------------|------------|
| `USE_WIFI` | Включить WiFi-транспорт |
| `USE_MQTT` | Включить код MQTT-клиента |
| `USE_HTTP` | Включить код HTTP-сервера |
| `USE_OTA` | Включить код OTA-обновлений |
| `USE_ZIGBEE` | Включить Zigbee-транспорт |
| `USE_THREAD` | Включить Thread-транспорт |
| `USE_BLE_SETUP` | Включить BLE-сервер для режима настройки |
| `USE_AP_SETUP` | Включить AP-режим для настройки |

**Пример использования в коде:**

```cpp
// transport_wifi.cpp — условная компиляция компонентов

#ifdef USE_HTTP
    #include "transport_http.h"
    HttpProtocol _http;
#endif

#ifdef USE_MQTT
    #include "transport_mqtt.h"
    MqttProtocol _mqtt;
#endif

#ifdef USE_BLE
    #include "transport_ble.h"
    BleServer _ble;
#endif

void WiFiTransport::update() {
    #ifdef USE_HTTP
        _http.update();
    #endif

    #ifdef USE_MQTT
        _mqtt.update();
    #endif

    #ifdef USE_BLE
        if (_state == STATE_SETUP_MODE) {
            _ble.update();
        }
    #endif
}
```

**Таблица соответствия:**

| Транспорт | USE_WIFI | USE_ZIGBEE | USE_THREAD | USE_MQTT | USE_HTTP | USE_BLE_SETUP |
|-----------|----------|------------|------------|----------|----------|---------------|
| **WiFi** | 1 | 0 | 0 | 1 | 1 | зависит от метода настройки |
| **Zigbee** | 0 | 1 | 0 | 0 | 0 | 0 |
| **Thread** | 0 | 0 | 1 | 0 | 0 | 0 |

**Примечание:** Флаги `USE_*` **не задаются** в `platformio.ini` и не определяются в транспортном слое. Они приходят из `settings.h` уже вычисленными.
