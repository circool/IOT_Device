## 1. Назначение

`TRANSPORT_HTTP` — прикладной протокол WiFi-транспорта, обеспечивающий:
- Визуальный интерфейс для пользователя через Web-страницы
- Оперативное управление устройством через HTTP-запросы
- Настройку параметров устройства
- Отображение текущего состояния
- OTA-обновления прошивки

**HTTP-протокол является частью WiFi-транспорта и работает поверх WiFi (как в STA, так и в AP-режиме).**

**HTTP не управляет флагами в `StateProvider`:** его работа полностью зависит от `link_ok` (устанавливается WiFi-транспортом). HTTP не является внешним сервисом, а лишь визуальным интерфейсом поверх сети.

## 3. Принципы

| Принцип | Описание |
|---------|----------|
| **Единый контракт** | HTTP получает данные через `publishState()` и `publishSettings()` — как и MQTT |
| **Синхронность** | HTTP — протокол запрос-ответ. Данные отдаются по запросу из буфера последнего состояния |
| **Нет провайдеров** | HTTP не требует от оркестратора реализации интерфейсов для получения данных |
| **Визуализация** | HTTP превращает структурированные данные в HTML-страницы |
| **Пассивность** | HTTP не управляет флагами в `StateProvider`. Его работа зависит от `link_ok` |
| **Инкапсуляция** | HTTP не имеет прямого доступа к `ConfigManager`, `StateProvider` или глобальным переменным |

## 4. Режимы работы

| Режим | Доступные страницы | Назначение | Когда активен |
|-------|-------------------|------------|---------------|
| **NORMAL** | `/` — состояние устройства | Отображение текущего состояния | Обычный режим WiFi-транспорта (STA) |
| | `/config` — настройки | Две формы на одной странице: | |
| | | 1. Настройки транспорта | |
| | | 2. Настройки устройства | |
| **SETUP** | `/` — страница ввода | Форма настроек транспорта (SSID, пароль, MQTT) | Режим настройки WiFi-транспорта (AP) |

### 4.1. Режим NORMAL

**Страница `/` (состояние устройства):**
- Отображает текущее состояние устройства
- Показывает показания датчиков (температура, влажность)
- Отображает статус актуатора (вкл/выкл, скорость)
- Показывает статус подключений (`link_ok`, `gateway_ok`, `link_quality`)
- Принимает оперативные команды через `/set`

**Страница `/config` (настройки):**
- Две независимые формы на одной странице:
  - **Настройки транспорта** — параметры канала связи (WiFi SSID/пароль, MQTT брокер/порт/логин/пароль)
  - **Настройки устройства** — бизнес-параметры (пороги, таймеры, режимы, скорость)
- Каждая форма имеет свой обработчик и сохраняется независимо

### 4.2. Режим SETUP

- Доступна только страница `/` — форма ввода учётных данных
- Показывает поля для ввода SSID, пароля (и MQTT, если необходимо)
- Все остальные маршруты редиректят на `/`
- После сохранения — проверка данных и переключение в обычный режим

### 4.3. Переключение режимов

Режимы переключаются **WiFi-транспортом** через публичный интерфейс:

```cpp
// WiFi-транспорт переключает HTTP-протокол
_http.setMode(HTTP_MODE_SETUP);   // Страница ввода
_http.setMode(HTTP_MODE_NORMAL);  // Страница состояния + настройки
```

## 5. Интерфейс

HTTP-протокол предоставляет WiFi-транспорту публичный интерфейс для управления:

### 5.1. Управление жизненным циклом

| Метод | Назначение | Вызов |
|-------|------------|-------|
| `init(server)` | Инициализация HTTP-сервера, регистрация маршрутов | Один раз в `setup()` |
| `begin(config)` | Запуск HTTP-сервера с конфигурацией | После инициализации |
| `update()` | Периодическая обработка запросов (`server.handleClient()`) | В `loop()` |

### 5.2. Управление режимами

| Метод | Назначение |
|-------|------------|
| `set_mode(mode)` | Переключить режим (NORMAL / SETUP) |
| `set_fields(fields)` | Установить, какие поля показывать на странице |
| `prefill_config(config)` | Предзаполнить поля известными данными |

### 5.3. Получение данных от транспорта

| Метод | Назначение |
|-------|------------|
| `update_state(state)` | Обновить буфер состояния для отображения |
| `update_settings(settings)` | Обновить буфер настроек для отображения |

## 6. Получение данных

HTTP-протокол получает данные через единый механизм публикации транспортной абстракции:

```cpp
// HTTP-протокол получает данные через publishState()
void HttpProtocol::updateState(const DeviceState* state) {
    _cachedState = *state;  // Сохраняем последнее состояние
}

void HttpProtocol::updateSettings(const DeviceConfig* settings) {
    _cachedSettings = *settings;  // Сохраняем последние настройки
}
```

**При обработке HTTP-запроса:**

```cpp
void HttpProtocol::handleRoot() {
    // Отдаём пользователю закэшированное состояние
    renderPage(&_cachedState, &_cachedSettings);
}
```

**Что это даёт:**
- HTTP и MQTT используют **один и тот же механизм** получения данных
- Нет дублирования логики
- Оркестратор не знает о внутреннем устройстве HTTP
- Архитектурная чистота соблюдена

**Важно:** HTTP не читает `StateProvider`. Он получает данные через `publishState()`, как и MQTT.

## 7. Принципы формирования страниц

HTTP-протокол формирует страницы по принципу **компоновки из готовых блоков** с учётом ограничений встроенных систем.

### 7.1. Хранение шаблонов

- Все статические HTML-шаблоны хранятся в PROGMEM (Flash-память).
- Это предотвращает нецелевое использование RAM для хранения строк.

```cpp
// Пример хранения шаблонов в PROGMEM
extern const char HTML_PAGE_START[] PROGMEM;
extern const char HTML_PAGE_END[] PROGMEM;
extern const char HTML_STYLE[] PROGMEM;
```

### 7.2. Рендеринг (компоновка)

- Страницы собираются из независимых типовых блоков (render-функций).
- Каждый блок отвечает за отображение одного элемента:
  - Карточка температуры (с цветовой индикацией)
  - Карточка влажности (с цветовой индикацией)
  - Состояние актуатора (карточка-ссылка)
  - Шкала скорости
  - Режим работы
  - Текстовое поле
  - Числовое поле
  - Чекбокс
- Блоки не знают о бизнес-логике — они работают только с переданными структурами (`DeviceState`, `DeviceConfig`).

```cpp
// Пример: компоновка страницы состояния из блоков
void HttpProtocol::renderStatusPage() {
    send(HTML_PAGE_START);
    renderHeader(&_cachedState);
    renderTemperatureBlock(&_cachedState);
    renderHumidityBlock(&_cachedState);
    renderStatusBlock(&_cachedState);
    renderSpeedBlock(&_cachedState);
    renderFooter();
    send(HTML_PAGE_END);
}
```

### 7.3. Источник данных

- HTTP-протокол получает данные для отображения **исключительно** через `updateState()` и `updateSettings()`.
- Данные хранятся в локальном буфере (`_cachedState`, `_cachedSettings`).
- **Запрещён прямой доступ к ConfigManager, StateProvider или глобальным переменным из HTTP-слоя.**

### 7.4. Визуальное представление

- Детальное описание страниц, блоков, полей и CSS-классов вынесено в `TRANSPORT_HTTP_SPEC.md`.
- HTTP-протокол использует эти блоки для компоновки, но не управляет их содержимым напрямую.

## 8. Маршруты

| URL | Метод | Назначение | Доступ |
|-----|-------|------------|--------|
| `/` | GET | Страница состояния устройства | NORMAL |
| `/config` | GET | Страница настроек (две формы) | NORMAL |
| `/save/transport` | POST | Сохранение настроек транспорта → `onConfigUpdate()` | NORMAL / SETUP |
| `/save/device` | POST | Сохранение настроек устройства → `onCommand()` | NORMAL |
| `/set` | GET | Оперативная команда | NORMAL |
| `/update` | GET/POST | OTA-обновление | NORMAL (если доступно) |

**Примечания:**
- В режиме SETUP все маршруты, кроме `/` и `/save/transport`, редиректят на `/`.
- `/save/transport` в режиме SETUP используется для сохранения WiFi/MQTT учётных данных.
- Обработчик `/save/device` отсутствует в режиме SETUP.

## 9. Взаимодействие с оркестратором

### 9.1. Передача команд

HTTP-протокол передаёт команды оркестратору через колбэк `onCommand` (установленный WiFi-транспортом):

| Маршрут | Действие | Команда |
|---------|----------|---------|
| `/set?state=on` | Включить | `CMD_STATE(true)` |
| `/set?state=off` | Выключить | `CMD_STATE(false)` |
| `/set?speed=75` | Скорость 75% | `CMD_SPEED(75)` |
| `/set?sensorMode=1` | Включить AUTO | `CMD_SET_SENSOR_CONTROL_MODE(true)` |
| `/set?adaptiveMode=1` | Включить адаптивный | `CMD_SET_ADAPTIVE_MODE(true)` |

### 9.2. Передача конфигурации

Страница `/config` содержит две независимые формы:

#### Форма настроек транспорта

```cpp
void HttpProtocol::handleSaveTransport() {
    TransportConfig config;
    config.wifiSsid = _server->arg("wifiSsid");
    config.wifiPassword = _server->arg("wifiPassword");
    config.mqttBroker = _server->arg("mqttBroker");
    config.mqttPort = _server->arg("mqttPort").toInt();
    config.mqttUser = _server->arg("mqttUser");
    config.mqttPassword = _server->arg("mqttPassword");
    // ...
    _onConfigUpdate(&config);  // ← отдельный колбэк для транспорта
}
```

#### Форма настроек устройства

```cpp
void HttpProtocol::handleSaveDevice() {
    DeviceConfig settings;
    settings.lowTemp = _server->arg("lowTemp").toFloat();
    settings.highTemp = _server->arg("highTemp").toFloat();
    settings.lowHum = _server->arg("lowHum").toFloat();
    settings.highHum = _server->arg("highHum").toFloat();
    settings.delaySeconds = _server->arg("delaySeconds").toInt();
    settings.maxOnTime = _server->arg("maxOnTime").toInt();
    settings.sensorMode = _server->arg("sensorMode") == "1";
    settings.adaptiveMode = _server->arg("adaptiveMode") == "1";
    settings.bootState = _server->arg("bootState") == "1";
    // ...
    TransportCommandData data;
    data.type = CMD_SET_ALL_SETTINGS;
    data.settings = settings;
    _onCommand(CMD_SET_ALL_SETTINGS, &data);  // ← отдельный колбэк для устройства
}
```

**Принцип:** Каждая форма вызывает свой колбэк, передавая только те данные, которые относятся к её области ответственности.

## 10. OTA-подсистема

OTA является подкомпонентом HTTP-протокола.

### 10.1. Назначение

Обновление прошивки через веб-интерфейс без физического подключения.

### 10.2. Доступность

| Условие | OTA доступен |
|---------|--------------|
| Flash < 2MB | ❌ Нет |
| Flash ≥ 2MB | ✅ Да |

### 10.3. Интерфейс

| Функция | Назначение |
|---------|------------|
| `ota_init(server)` | Инициализация OTA (регистрация `/update`) |
| `ota_is_available()` | Проверка доступности OTA |

### 10.4. Принцип работы

1. Пользователь загружает `.bin` файл через форму на `/update`
2. Библиотека ElegantOTA обрабатывает загрузку и проверку
3. После успешной загрузки — автоматическая перезагрузка
4. При ошибке — отображение сообщения

## 11. Валидация и обратная связь

### 11.1. Валидация

**Клиентская (браузер):**
- Атрибуты `required` — обязательные поля
- Атрибуты `min` / `max` — диапазоны значений
- Атрибут `type="number"` — числовые поля
- Генерируются на основе констант из `settings.h`

**Серверная (защита от обхода браузера):**
- Проверка обязательных полей
- Проверка диапазонов (используются те же константы)
- При ошибке — страница с описанием проблемы

```cpp
// Пример серверной валидации
#include "settings.h"

void HttpProtocol::handleSaveDevice() {
    float lowTemp = _server->arg("lowTemp").toFloat();
    if (lowTemp < TEMP_MIN || lowTemp > TEMP_MAX) {
        sendError("Low temperature out of range");
        return;
    }
    // ... остальные проверки
}
```

### 11.2. Обратная связь

После отправки формы:
1. Открывается страница результата:
   - **Успех** — зелёное уведомление
   - **Ошибка** — красное уведомление с описанием
2. Через 2–3 секунды — автоматический редирект на `/config`

**Принцип:** Пользователь всегда знает, успешно ли сохранены настройки, и возвращается на страницу настроек для продолжения работы.
