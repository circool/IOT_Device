## 1. Введение

### 1.1. Назначение документа

Документ описывает архитектуру встраиваемого ПО для семейства устройств умного дома на базе ESP8266/ESP32. Предназначен для команды разработчиков и содержит:

- Архитектурные принципы, принятые в проекте
- Структуру проекта, перечень файлов и крткое описание слоёв
- Правила именования файлов, слоёв, функций и методов 
- Требования к коду и документации
---
## 2. Архитектурные принципы

| Принцип | Описание |
|---------|----------|
| **Единая кодовая база** | Один репозиторий, сборка разных бинарников через флаги (`-DDEVICE_TYPE`, `-DTRANSPORT_TYPE`) |
| **Разделение ответственности** | Каждый слой отвечает за одну функциональную область |
| **Инверсия зависимостей** | Бизнес-логика не зависит от транспорта и инфраструктуры |
| **Автономность** | Устройство работает без внешних каналов связи |
| **Config ≠ State** | Постоянные параметры (EEPROM) и оперативное состояние (RAM) — разные структуры |
| **Централизованное управление** | Критические операции (`config_save()`, `ESP.restart()`) выполняются централизованно |
| **Единый интерфейс слоёв** | Все слои с состоянием и периодической логикой реализуют `init()` и `update()`. Оркестратор вызывает их в `setup()` и `loop()` соответственно. |
| **Заглушки для отсутствующих компонентов** | Если компонент может отсутствовать на этапе компиляции (например, сенсор для TYPE 3), его API должен быть реализован в виде заглушек (inline-функции). Каждая заглушка (включая методы классов) вместо doxygen должна предваряться кратким пояснением причины появления заглушки - ```// Заглушка - Слой/метод/класс/FEATURE_...ENAVLED/итп ... отключен```. Оркестратор не должен содержать `#ifdef` для проверки наличия компонента. |

## 3.2. Краткое описание слоев

### 3.2.1 main - Оркестратор

**Назначение:** Выполняет общую оркестрацию слоев при инициализации и периодическом обновлении.

**Особенности:** Работает с слоями обеспечивая обмен данными между ними. Инициирует все слои, периодически их опрашивает и при необходимости запускает или останавливает.

**Детали:** `ORCHESTRATOR.md`

### 3.2.2. system_state — Состояние системы

**Назначение:** Хранение глобального состояния устройства. Используется для принятия решений (например, LED определяет режим по битам)

**Особенности:**
- Слой читается всеми заинтересованными слоями, но изменения допустимо выполнять только связанным слоям

**Детали:** `SYSTEM_STATE.md`

### 3.2.3. config_manager — Конфигурация устройства

**Назначение:** хранение постоянных параметров в энергонезависимой памяти, оперативного состояния в RAM

**Особенности:**

**Детали:** `CONFIG_AND_STATE.md`

### 3.2.4. device_controller — Контроллер устройства

**Назначение:** центральный слой, содержащий всю бизнес-логику устройства.

**Особенности:** Хранит свое состояние и взаимодействует с подчиненными слоями - датчиком и актуатором

**Детали:** `DEVICE_CONTROLLER.md`

### 3.2.5. sensor / actuator_base / fan_actuator / switch_actuator — Исполнительные механизмы

**Назначение:** управление физическими выходами. Отслеживание оперативного внутреннего состояния.

**Sensor:**
- Датчик температуры/влажности 

**ActuatorBase (базовый класс):**
- Общие каналы управления

**FanActuator (наследует ActuatorBase):**
- Каналы управления характерные для вертилятора

**SwitchActuator (наследует ActuatorBase):**
- Каналы управления характерные для выключателя


**Детали:** `ACTUATOR_SENSOR.md`

### 3.2.6. transport — Транспортный слой

**Назначение:** Абстракция каналов связи - единый интерфейс для MQTT, Zigbee, Matter.

**Особенности** содержит:
- Реализацию протокола обмена данными ZigBee
- Каналы взаимодействия по протоколу MQTT
- Каналы взаимодействия по протоколу Matter

**Детали:** `TRANSPORT_ABSTRACTION.md`, `TRANSPORT_MQTT.md`, `TRANSPORT_ZIGBEE.md`, `TRANSPORT_MATTER.md`

### 3.2.7. web_manager — Веб-сервер и интерфейс взаимодействия

**Назначение:** реализует сервер и HTTP-интерфейс для мониторинга состояния и настройки параметров.

**Детали:** `TRANSPORT_ABSTRACTION.md`, `TRANSPORT_WEB.md`, `WEB_OTA_MANAGER.md`

### 3.2.8. provisioning_manager — Комиссионинг (настройка)

**Назначение:** интеграция устройства в экосистему умного дома.

**Особенности:** Выбирает необходимый протокол и взаимодействует с подчиненными слоями: 
- ble_server : BLE-сервер (ESP32)
- ap_server : AP-точка доступа (все платформы)
- zigbee_server : Zigbee-сервер (ESP32-C6 / ESP32-H2)
- matter_server : Matter-сервер (ESP32-C6 / ESP32-H2)

**Детали:** `PROVISIONING_MANAGER.md`

### 3.2.9. web_ota_manager
**Назначение:** реализует механизм обновления прошивки по воздуху.
**Особенности**: обертка для методов стандартной библиотеки 
**Детали:** `WEB_OTA_MANAGER.md`, `WEB_MANAGER.md`

### 3.2.10. led_manager — Светодиодная индикация

**Назначение:** визуальная индикация состояния.

**Детали:** `LED_MANAGER.md`

### 3.2.11. reset_btn — Кнопка сброса

**Назначение:** механизм определения состояния кнопки сброса.

**Особенности:**
- Подсчёт времени удержания кнопки в трех степенях продолжительности

**Детали:** `RESET_BUTTON_MANAGER.md`

### 3.2.12. restart_manager — Менеджер перезагрузок

**Назначение:** централизованное управление перезагрузкой устройства.

**Детали:** `RESTART_MANAGER.md`

### 3.2.13. wdt_manager — Сторожевой таймер

**Назначение:** защита от зависаний микроконтроллера.

**Детали:** `WDT_MANAGER.md`

### 3.2.14. wifi_manager — Управление WiFi (STA-режим)

**Назначение:** управление WiFi-подключением устройства в режиме клиента (STA).

**Детали:** `WIFI_MANAGER.md`, `TRANSPORT_ABSTRACTION.md`

### 3.2.15. logger — Логирование

**Назначение:** вывод диагностической информации в Serial.

**Особенности:**
- Слой не имеет состояния и не требует вызова  в цикле
- Инициализируется первым для логирования всех последующих шагов

**Детали:** `LOGGER.md`

### 3.2.16. settings - Настройка и валидация

**Назначение:** Настройка всех основных констант, инициализация значений по умолчанию, проверка совместимости подчиненно-зависимых флагов;

**Особенности:** реализует проверки зависимостей на этапе компиляции.
Некорректные комбинации флагов должны вызывать ошибки сборки с понятным сообщением.

**Детали:** `BUILD_AND_CONFIG.md`, раздел 10.

## 4. Правила наименования слоёв

### 4.1.1. Постфиксы для типов слоёв

Каждый слой должен иметь постфикс, отражающий его тип и ответственность:

| Постфикс | Назначение | Пример |
|----------|------------|--------|
| `_manager` | Управление ресурсом/состоянием (синглтон или глобальный объект) | `config_manager`, `wifi_manager`, `restart_manager` |
| `_server` | Приём входящих соединений (HTTP, BLE) | `web_server`, `ble_provisioning_server` |
| `_controller` | Бизнес-логика, принятие решений | `device_controller` |
| `_actuator` | Управление физическим выходом (GPIO, ШИМ) | `fan_actuator`, `switch_actuator` |
| `_provider` | Предоставление данных для другого слоя (адаптер) | `web_status_provider` |
| `_transport` | Реализация протокола связи | `mqtt_transport`, `zigbee_transport` |
| `_base` | Базовый класс/интерфейс | `actuator_base` |
| `_common` | Общие функции для группы слоёв | `http_common` |
| `_templates` | Константы/шаблоны (PROGMEM) | `html_templates` |

### 4.1.2. Именование файлов

- Все файлы слоёв — `snake_case`
- Постфикс обязателен для всех слоёв с состоянием
- Исключение: файлы с макросами (`settings.h`, `credentials.h`)

### 4.1.3. Именование классов и структур

- Классы — `PascalCase` + постфикс (`ConfigManager`, `DeviceController`)
- Структуры — `PascalCase` без постфикса (`ConfigData`, `Transport`)
- Enum — `PascalCase` (тип) + `UPPER_CASE` (значения)


### 4.1.4. Единый интерфейс слоёв

Все слои, требующие инициализации и периодической обработки, реализуют единый интерфейс насколько это возможно:

```cpp
class Layer {
public:
    void init();    // Вызывается один раз в setup()
    void update();  // Вызывается каждый цикл в loop()
    bool start();   // Вызывается по требованию
    bool stop();    // Вызывается по требованию
};
```
### 4.1.5. Проверка соответствия (lint)

При code review проверять:
- [ ] Файл имеет корректный постфикс согласно типу
- [ ] Класс имеет тот же постфикс, что и файл
- [ ] Для слоя есть документация `ИМЯ_СЛОЯ.md` (если слой не тривиальный)

## 5. Требования к коду и документации

### 5.1. Стиль

- `snake_case` для функций и переменных
- `PascalCase` для классов и структур
- Doxygen-комментарии для всех методов и классов
- Файлы начинаются с комментария с названием и назначением

### 5.2. Память

- **Запрещено** динамическое выделение (`new`, `malloc`) в runtime
- Все объекты создаются статически (в main.cpp)
- Использовать `PROGMEM` для строковых констант (HTML, логи)
- Избегать `std::function` (использовать указатели на функции + контекст)

### 5.3. Обработка ошибок

- Все операции с датчиками должны иметь таймауты
- При ошибке датчика — `sensorValid = false`, публикация с `valid = false`
- При ошибке конфигурации — переход в AP-режим
- WDT должен быть включён в production

### 5.4. Логирование

- Критические события → `XLOG_ERROR`
- Переключение режимов → `XLOG_INFO`
- Показания датчика → `XLOG_DEBUG`
- Production: `XLOG_LEVEL = 2` (WARN)

### 5.5. Документирование слоёв

**Принципы оформления документации на слои:**

| # | Принцип | Описание |
|---|---------|----------|
| 1 | **Архитектура vs реализация** | В `ARCHITECTURE.md` описывается **назначение, ответственность и связи** слоя. Детали API, структур данных и алгоритмов выносятся в отдельный `LAYER_NAME.md`. |
| 2 | **Правила, не примеры** | В документации описываются **правила и принципы**, а не приводятся примеры кода. Исключение — ключевые архитектурные контракты (интерфейсы). |
| 3 | **Единая структура** | Каждый документ слоя имеет единую структуру: Назначение → Ответственность → API (описание методов без кода) → Интеграция → Настройка |
| 4 | **Минимум кода** | Код в документации допустим **только** для: <br>— архитектурных контрактов (интерфейсы, структуры данных) <br>— критических алгоритмов, которые сложно описать словами <br>— **Запрещено** приводить примеры использования в архитектурных документах |
| 5 | **Разделение по уровням** | <br>— `ARCHITECTURE.md`: только "что делает слой" и "как взаимодействует" <br>— `LAYER_NAME.md`: "как это реализовано" (API, структуры, алгоритмы) |
| 6 | **Актуальность** | Документация должна соответствовать текущей реализации. Устаревшие описания удаляются или помечаются `@deprecated`. |
| 7 | **Лаконичность** | Документация должна быть компактной и не описывать случи "НЕ ДЕЛАЕТ", "НЕ ЧИТАЕТ", "НЕ ЗАВИСИТ" и подоюное. |

### 5.6. Документирование файлов кода

### 5.6.1. Файлы должны начинаться с doxygen описания


```cpp
/**
 * @file logger.cpp
 * @brief Реализация логгера
 * @note (при необходимости)
 * @todo (при необходимости)
 * @param (при необходимости)
 * @return (при необходимости)
 */
```

В заголовочных файлах каждая сущность должна содержать doxygen пояснения


### 5.6.2. Пояснения для заглушек
Описания заглушек должны содержать doxygen указание на заглушку с описанием причины  
```cpp
/**
 * @brief Заглушка — ... отключён
 */
```
### 5.6.3. Мертвый код
Все неиспользуемые сущности должны быть помечены как `@deprecated`
