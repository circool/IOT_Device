## 1. Введение

### 1.1. Назначение документа

Документ описывает архитектуру встраиваемого ПО для семейства устройств умного дома на базе ESP8266/ESP32. Предназначен для команды разработчиков и содержит:

- Структуру модулей и их ответственность
- Интерфейсы взаимодействия между слоями
- Правила конфигурирования и сборки
- Принципы работы с параметрами (Config vs State)

Документ **не описывает** бизнес-логику конкретных типов устройств — это уровень реализации, описанный в специализированных документах.

---

### 1.2. Принципы архитектуры

| Принцип | Описание |
|---------|----------|
| **Единая кодовая база** | Один репозиторий, сборка разных бинарников через флаги (`-DDEVICE_TYPE`, `-DTRANSPORT_TYPE`) |
| **Разделение ответственности** | Каждый слой отвечает за одну функциональную область |
| **Инверсия зависимостей** | Бизнес-логика не зависит от транспорта и инфраструктуры |
| **Автономность** | Устройство работает без внешних каналов связи |
| **Config ≠ State** | Постоянные параметры (EEPROM) и оперативное состояние (RAM) — разные структуры |
| **Централизованное управление** | Критические операции (`config_save()`, `ESP.restart()`) выполняются централизованно |
| **Единый интерфейс слоёв** | Все слои с состоянием и периодической логикой реализуют `init()` и `update()`. Оркестратор вызывает их в `setup()` и `loop()` соответственно. |
| **Заглушки для отсутствующих компонентов** | Если компонент может отсутствовать на этапе компиляции (например, сенсор для TYPE 3), его API должен быть реализован в виде заглушек (inline-функции). Каждая заглушка (включая методы классов) вместо doxygen должна предваряться кратким пояснением причины появления заглушки - ```// Заглушка - Слой/метод/класс/FEATURE_...ENAVLED/итп ... отключен```. Оркестратор не должен содержать `#ifdef` для проверки наличия компонента. |

## 2. Структура проекта

## 2.1. Правила наименования слоёв

### 2.1.1. Постфиксы для типов слоёв

Каждый слой должен иметь постфикс, отражающий его тип и ответственность:

| Постфикс | Назначение | Пример |
|----------|------------|--------|
| `_manager` | Управление ресурсом/состоянием (синглтон или глобальный объект) | `config_manager`, `wifi_manager`, `restart_manager` |
| `_server` | Приём входящих соединений (HTTP, BLE) | `web_server`, `ble_provisioning_server` |
| `_controller` | Бизнес-логика, принятие решений | `device_controller` |
| `_actuator` | Управление физическим выходом (GPIO, ШИМ) | `fan_actuator`, `switch_actuator` |
| `_provider` | Предоставление данных для другого слоя (адаптер) | `web_status_provider` |
| `_transport` | Реализация протокола связи | `mqtt_transport`, `zigbee_transport` |
| `_base` | Базовый класс/интерфейс | `actuator_base` |
| `_common` | Общие функции для группы слоёв | `http_common` |
| `_templates` | Константы/шаблоны (PROGMEM) | `html_templates` |

### 2.1.2. Именование файлов

- Все файлы слоёв — `snake_case`
- Постфикс обязателен для всех слоёв с состоянием
- Исключение: файлы с макросами (`settings.h`, `credentials.h`)

### 2.1.3. Именование классов и структур

- Классы — `PascalCase` + постфикс (`ConfigManager`, `DeviceController`)
- Структуры — `PascalCase` без постфикса (`ConfigData`, `Transport`)
- Enum — `PascalCase` (тип) + `UPPER_CASE` (значения)

### 2.1.4. Проверка соответствия (lint)

При code review проверять:
- [ ] Файл имеет корректный постфикс согласно типу
- [ ] Класс имеет тот же постфикс, что и файл
- [ ] Для слоя есть документация `ИМЯ_СЛОЯ.md` (если слой не тривиальный)

## 3. Слои и их ответственность

### 3.1. system_state — Состояние системы

**Назначение:** битовая маска глобального состояния устройства.

**Ответственность:**
- Хранение флагов: `STATE_WIFI_OK`, `STATE_MQTT_OK`, `STATE_PROVISIONING`, `STATE_EMERGENCY`, `STATE_RESTART`, `STATE_BUTTON_PRESSED`
- API: `set_bit()`, `clear_bit()`, `has_bit()`, `get_bits()`

**Особенности:**
- Слой читается всеми заинтересованными слоями, но изменения допустимо выполнять только связанным слоям
- Используется для принятия решений (например, LED определяет режим по битам)

**Детали:** `SYSTEM_STATE.md`

---

### 3.2. config_manager — Конфигурация (EEPROM)

**Назначение:** хранение постоянных параметров в энергонезависимой памяти.

**Ответственность:**
- Чтение/запись EEPROM с проверкой CRC
- Валидация параметров (диапазоны, длины строк)
- Предоставление значений по умолчанию
- Генерация deviceId из MAC-адреса

**Структура ConfigData:** описана в `CONFIG_AND_STATE.md` (раздел 3).

**Ключевые методы:**

| Метод | Назначение |
|-------|------------|
| `getInstance()` | Доступ к синглтону |
| `init()` | Загрузка из EEPROM или defaults |
| `get()` | Получение указателя на ConfigData |
| `save()` | Запись в EEPROM |
| `reset()` | Сброс к заводским настройкам |
| `isValid()` | Проверка валидности (CRC + magic) |
| `setDefaults()` | Заполнение значениями по умолчанию |

**Важно:** ConfigManager **не знает** о DeviceController, State, транспорте. Он только хранит данные.

---

### 3.3. device_controller — Бизнес-логика (планируется)

**Назначение:** центральный слой, содержащий всю бизнес-логику устройства.

**Ответственность:**
- Хранение оперативного состояния (`OperationalState`)
- Принятие решений на основе:
  - Показаний датчика (из `Sensor`)
  - Порогов из `Config`
  - Таймеров из `Actuator`
  - Режимов (MANUAL/AUTOMATIC)
- Управление актуатором через вызовы его методов
- Вызов колбэка при изменении состояния

**Структура OperationalState:** описана в `CONFIG_AND_STATE.md` (раздел 4) и детально в `DEVICE_CONTROLLER.md` (раздел 3).

**Колбэк:**
```cpp
typedef void (*StateCallback)(const DeviceState* state, bool needSave);
```
- `needSave = true` — изменился постоянный параметр (вызвать `config_save()`)
- `needSave = false` — изменился только оперативный параметр (только публикация)

**DeviceController НЕ ЗНАЕТ:**
- О ConfigManager (получает Config через `init()`)
- О транспорте (MQTT, Web, Zigbee, Matter)
- О EEPROM
- О пинах (управляет через Actuator)

**DeviceController ЗНАЕТ:**
- Структуру `ConfigData` (для чтения порогов, таймеров)
- Структуру `OperationalState` (для хранения состояния)
- Интерфейсы `Sensor` и `Actuator`

**Детали бизнес-логики:** `DEVICE_CONTROLLER.md`

---

### 3.4. actuator_base / fan_actuator / switch_actuator — Исполнительные механизмы

**Назначение:** управление физическими выходами (GPIO, ШИМ). Отслеживание оперативного внутреннего состояния.

**Ответственность:**
- Включение/выключение пина
- ШИМ-управление (для вентилятора)
- Отслеживание времени непрерывной работы (`onTimeSec`)
- Вычисление `emergency` (превышение `maxOnTime`)
- Отложенное включение (`delaySeconds`)

**ActuatorBase (базовый класс):**
- Управление пином (ON/OFF)
- Таймер отложенного включения
- Таймер аварийного отключения (вычисляет `emergency`)

**FanActuator (наследует ActuatorBase):**
- ШИМ-управление скоростью
- Стартовый импульс для раскрутки
- Флаг `adaptiveMode` (логика в DeviceController)

**SwitchActuator (наследует ActuatorBase):**
- Только ON/OFF (без ШИМ)

**Колбэки:**

| Колбэк | Назначение |
|--------|------------|
| `onSetPhysicalCallback` | Вызывается при изменении состояния пина |
| `onForceStopCallback` | Вызывается при аварийной остановке (emergency) |
| `onManualCommandCallback` | Вызывается при ручной команде |

**Actuator НЕ ЗНАЕТ:**
- О ConfigManager (получает параметры через конструктор)
- О DeviceController
- О бизнес-логике (порогах, режимах)

**Actuator ЗНАЕТ:**
- Свой пин
- `maxOnTime` (получил при создании)
- `delaySeconds` (получил при создании)
- Своё состояние (`_state`, `_emergency`, `_onTimeSec`)

**Детали:** `ACTUATOR_SENSOR.md`

---

### 3.5. sensor — Датчик температуры/влажности

**Назначение:** чтение физических показаний.

**Ответственность:**
- Чтение AHT10 (I2C) или DHT (GPIO)
- Валидация данных (проверка на `isnan`, таймауты)
- Вычисление `sensorValid` (успешность чтения)
- Предоставление показаний и статуса

**Ключевые методы:**

| Метод | Назначение |
|-------|------------|
| `sensor_init()` | Инициализация I2C/GPIO |
| `sensor_update()` | Чтение данных (с интервалом) |
| `sensor_getTemperature()` | Температура (°C) |
| `sensor_getHumidity()` | Влажность (%) |
| `sensor_isOk()` | Валидность данных |
| `sensor_getError()` | Текст ошибки |
| `sensor_getHumRate()` | Скорость изменения влажности (%/сек) |

**Sensor НЕ ЗНАЕТ:**
- О ConfigManager
- О DeviceController
- О бизнес-логике

**Sensor ЗНАЕТ:**
- Свои пины (SDA/SCL или GPIO)
- Минимальный интервал опроса (из даташита)
- Своё состояние (`_temperature`, `_humidity`, `_valid`)

**Детали:** `ACTUATOR_SENSOR.md`

### 3.6. transport — Абстракция каналов связи

**Назначение:** единый интерфейс для MQTT, Zigbee, Matter.

**Реализация:** структура с указателями на функции (без `std::function`).

```cpp
struct Transport {
    // Управление
    bool (*begin)(Client* client, const ConfigData* config);
    void (*update)();
    bool (*isConnected)();
    void (*disconnect)();
    
    // Публикация
    void (*publishOnline)();
    void (*publishState)(bool on);
    void (*publishSpeed)(int percent);
    void (*publishDelaySec)(int seconds);
    void (*publishMaxOnTime)(uint32_t seconds);
    void (*publishSensorControlMode)(bool enabled);
    void (*publishSensor)(float temp, float hum);
    void (*publishAdaptiveMode)(bool enabled);
    void (*publishThresholds)(float lowTemp, float highTemp, float lowHum, float highHum);
    void (*publishRSSI)(int rssi);
    void (*publishVersion)(const char* version);
    void (*publishResetReason)(const char* reason);
    
    // Регистрация колбэков (брокер → устройство)
    void (*onState)(TransportBoolCallback callback, void* context);
    void (*onSpeed)(TransportIntCallback callback, void* context);
    void (*onDelaySec)(TransportIntCallback callback, void* context);
    void (*onMaxOnTime)(TransportUintCallback callback, void* context);
    void (*onSensorControlMode)(TransportBoolCallback callback, void* context);
    void (*onAdaptiveMode)(TransportBoolCallback callback, void* context);
    void (*onLowTemp)(TransportFloatCallback callback, void* context);
    void (*onHighTemp)(TransportFloatCallback callback, void* context);
    void (*onLowHum)(TransportFloatCallback callback, void* context);
    void (*onHighHum)(TransportFloatCallback callback, void* context);
    void (*onReset)(TransportVoidCallback callback, void* context);
};
```

**Фабрика:**

```cpp
Transport* createTransport() {
    #if TRANSPORT_TYPE == TRANSPORT_TYPE_WIFI
        #if FEATURE_MQTT_ENABLED == 1
            return getMQTTTransport();
        #else
            return nullptr;
        #endif
    #elif TRANSPORT_TYPE == TRANSPORT_TYPE_ZIGBEE
        return getZigbeeTransport();
    #else
        return nullptr;
    #endif
}
```

**Transport НЕ ЗНАЕТ:**
- О структуре ConfigData (работает с `PublicationData`)
- О DeviceController (только колбэки)
- О бизнес-логике

**Transport ЗНАЕТ:**
- Свой протокол (MQTT/Zigbee)
- Топики / кластеры
- Формат сериализации

**Детали:** `TRANSPORT_ABSTRACTION.md`, `TRANSPORT_MQTT.md`, `TRANSPORT_ZIGBEE.md`, `TRANSPORT_MATTER.md`

### 3.7. MQTTManager — MQTT-клиент

### 3.8. Web — Веб-интерфейс

**Назначение:** HTTP-интерфейс для настройки и мониторинга.

**Ответственность:**

- Отображение страницы конфигурации (`/config`)

**IWebStatusProvider:**

```cpp
class IWebStatusProvider {
public:
    virtual ~IWebStatusProvider() = default;
    
    // Основная информация
    virtual bool isDeviceOn() const = 0;
    virtual bool isEmergencyStop() const = 0;
    virtual bool isDelayActive() const = 0;
    virtual unsigned long getDelayTimer() const = 0;
    virtual unsigned long getStartTime() const = 0;
    
    // Вентилятор (TYPE 1)
    virtual int getSpeedPercent() const = 0;
    virtual bool isAdaptiveModeActive() const = 0;
    
    // Датчик (TYPE 1,2)
    virtual bool isSensorOk() const = 0;
    virtual float getTemperature() const = 0;
    virtual float getHumidity() const = 0;
    virtual const char* getSensorError() const = 0;
    
    // Подключения
    virtual bool isMqttConnected() const = 0;
    virtual int getWifiRssi() const = 0;
    
    // Параметры из Config
    virtual float getLowTemp() const = 0;
    virtual float getHighTemp() const = 0;
    virtual float getLowHum() const = 0;
    virtual float getHighHum() const = 0;
    virtual int getDelaySeconds() const = 0;
    virtual uint32_t getMaxOnTime() const = 0;
    virtual int getSensorInterval() const = 0;
    virtual bool isSensorControlMode() const = 0;
};
```

**Реализации:** `FanWebStatusProvider`, `SensorWebStatusProvider`, `SwitchWebStatusProvider`.

**Команды от Web к оркестратору:**

```cpp
// Флаги для оркестратора
extern volatile bool g_webConfigPending;   // Новые настройки от /save
```

**Интеграция:**
- Оркестратор в `loop()` проверяет стадию
- При `STAGE_3S` (удержание >3 секунд) вызывает `config_reset()` и `restart_request()`

### 3.13. restart_manager — Менеджер перезагрузок

**Назначение:** централизованное управление перезагрузкой устройства.

**Ответственность:**
- Приём запроса на перезагрузку из любого слоя (`restart_request()`)
- Выдержка задержки перед перезагрузкой (для отправки логов и завершения операций)
- **Единственный вызов `ESP.restart()`** во всей прошивке

**Важно:** Все слои вызывают `restart_request()`, но **только** `restart_manager.cpp` вызывает `ESP.restart()`. Это обеспечивает:
- Единую точку управления перезагрузкой
- Возможность добавить логирование перед перезагрузкой
- Защиту от множественных перезагрузок

**Детали:** `RESTART_MANAGER.md`

### 3.14. wdt_manager — Сторожевой таймер

**Назначение:** защита от зависаний микроконтроллера.

**Ответственность:**
- Инициализация аппаратного сторожевого таймера
- Периодический сброс WDT в цикле `loop()` для подтверждения работоспособности
- Остановка WDT перед длительными операциями (запись EEPROM, перезагрузка)
- Восстановление WDT после завершения критических операций

**Особенности:**

- При зависании устройства WDT автоматически перезагружает его

### 3.15. logger — Логирование

**Назначение:** вывод диагностической информации в Serial.

**Ответственность:**
- Фильтрация сообщений по уровню важности (ERROR, WARN, INFO, DEBUG)
- Фильтрация по категориям (битовая маска для отладки отдельных компонентов)
- Цветной вывод в консоль (ANSI-коды)

**Особенности:**
- Слой не имеет состояния и не требует вызова `update()` в цикле

**Детали:** `LOGGER.md`

### 3.16. wifi_manager — Управление WiFi (STA-режим)

**Назначение:** управление WiFi-подключением устройства в режиме клиента (STA).

**Ответственность:**
- Подключение к WiFi-сети (STA-режим)
- Мониторинг состояния подключения
- Автоматическое переподключение при потере связи
- Управление флагом `STATE_WIFI_OK` в SystemState
- Сканирование доступных сетей (опционально, для отладки)

**Важно:** AP-режим (точка доступа) **не входит** в ответственность WiFi-менеджера. 
AP-режим используется только для провизионинга и полностью вынесен в слой `provisioning`.

**Интеграция:**
- Оркестратор проверяет `STATE_WIFI_OK` для принятия решений
- При потере WiFi на время `WIFI_FALLBACK_TIMEOUT_MS` оркестратор запускает провизионинг
- Transport (MQTT) использует WiFi-клиент для подключения к брокеру
- WiFi-менеджер **самостоятельно** переключается из AP в STA после завершения провизионинга

**Детали:** `WIFI_MANAGER.md`

### 3.17. main.cpp — Оркестратор

**Назначение:** центральный управляющий слой, который связывает все компоненты системы. Оркестратор **не содержит бизнес-логики**, а только инициализирует и координирует работу слоёв.

**Ответственность:**
- Инициализация всех слоёв в правильном порядке (`setup()`)
- Периодический вызов `update()` всех слоёв в правильном порядке (`loop()`)
- Регистрация колбэков между слоями (транспорт → DeviceController)
- Обработка флагов от Web-слоя (`g_webConfigPending`, `g_webCommandPending`, `g_webRestartPending`)
- Определение режима LED на основе `SystemState`
- Принятие решения о запуске провизионинга при потере WiFi
- Единственный слой, который вызывает `config_save()` (через колбэк от DeviceController)

**Оркестратор НЕ ЗНАЕТ:**
- Внутреннюю реализацию слоёв (только их публичные API)
- Бизнес-логику (она в DeviceController)
- Детали транспорта (только интерфейс Transport)

**Оркестратор ЗНАЕТ:**
- Порядок инициализации всех слоёв
- Порядок вызова `update()` всех слоёв
- Флаги межслойного взаимодействия (`g_web*`)
- `SystemState` (читает биты для принятия решений)

**Особенности:**
- Оркестратор — **единственное место**, где создаются глобальные объекты слоёв
- Оркестратор — **единственное место**, где регистрируются колбэки между слоями
- Оркестратор не должен содержать `#ifdef` для проверки наличия компонентов (используются заглушки)

**Детали:** `ORCHESTRATOR.md`

### 4.1.1. Единый интерфейс слоёв

Все слои, требующие инициализации и периодической обработки, реализуют единый интерфейс:

```cpp
class Layer {
public:
    void init();    // Вызывается один раз в setup()
    void update();  // Вызывается каждый цикл в loop()
};
```
Оркестратор (main.cpp) вызывает init() у всех слоёв в setup() и update() у всех в loop().

Исключения: только слои без состояния (например, Logger).


### 4.2. Порядок инициализации (setup)

1. **Logger** — чтобы логировать все последующие шаги
2. **ConfigManager** — загрузка из EEPROM
3. **SystemState** — инициализация битовой маски
4. **WDT** — сторожевой таймер
5. **Sensor** — инициализация датчика (если нужен)
6. **Actuator** — инициализация пина с параметрами из Config
7. **DeviceController** — инициализация с передачей Config, Sensor, Actuator
8. **Transport** — создание через фабрику (`createTransport()`)
9. **Web** — инициализация, регистрация IWebStatusProvider
10. **OTA** — инициализация (если включена)
11. **LED** — инициализация пина
12. **ResetButton** — инициализация кнопки
13. **WiFi** — запуск STA (если Config валиден) или AP (если нет)
14. **Provisioning** — запуск (если Config невалиден)
15. **RestartManager** — подготовка к работе

---

### 4.3. Порядок выполнения (loop)

1. **WDT::update()** — сброс сторожевого таймера
2. **ResetButton::update()** — обновление состояния кнопки
3. **Sensor::update()** — чтение датчика (с интервалом)
4. **DeviceController::update()** — бизнес-логика (пороги, таймеры, режимы)
5. **Actuator::update()** — обновление таймеров (maxOnTime, delay)
6. **Transport::update()** — обработка MQTT/Zigbee
7. **Web::update()** — обработка HTTP-запросов
8. **LED::update()** — обновление светодиода
9. **RestartManager::update()** — проверка необходимости перезагрузки
10. **delay(10)** — небольшая задержка

## 5. Config vs State (ключевое решение)

### 5.1. Принцип разделения

| Категория | Параметры | Хранилище | Сохранение в EEPROM |
|-----------|-----------|-----------|---------------------|
| **Постоянные (Config)** | WiFi, MQTT, пороги, таймеры, режимы | EEPROM | **ДА** (немедленно) |
| **Оперативные (State)** | `isOn`, `speed`, `manualMode`, `timerMode`, `delayRemainSec` | RAM | **НЕТ** |
| **Вычисляемые** | `emergency`, `onTimeSec`, `sensorValid`, `temperature`, `humidity` | RAM | **НЕТ** |

### 5.2. Кто вычисляет что

| Поле | Вычисляется в |
|------|---------------|
| `emergency` | **Actuator** (на основе `maxOnTime` и `_onTimeSec`) |
| `onTimeSec` | **Actuator** (время непрерывной работы) |
| `sensorValid` | **Sensor** (успешность чтения) |
| `temperature` / `humidity` | **Sensor** (физические показания) |
| `manualMode` | **DeviceController** (на основе команд пользователя) |
| `speed` (адаптивная) | **DeviceController** (на основе порогов и показаний) |

**Детали:** `CONFIG_AND_STATE.md`, `DEVICE_CONTROLLER.md`


### 5.3. Поток изменения постоянного параметра

```
1. Пользователь отправляет команду через MQTT: {prefix}/c/delaySec = 120
2. Transport → колбэк в оркестраторе
3. Оркестратор → DeviceController::setPermanentParam(PARAM_DELAY_SEC, 120)
4. DeviceController:
   a. Меняет _state.config.delaySeconds = 120
   b. Вызывает колбэк _stateCallback(&_state, true)   // needSave = true
5. Оркестратор в колбэке:
   a. Вызывает config_save(&_state.config)  // запись в EEPROM
   b. Вызывает transport->publish()         // публикация нового состояния
```

---

### 5.4. Поток изменения оперативного параметра

```
1. Пользователь отправляет команду через MQTT: {prefix}/c/state = ON
2. Transport → колбэк в оркестраторе
3. Оркестратор → DeviceController::setOperationalParam(PARAM_STATE, true)
4. DeviceController:
   a. Меняет _state.op.isOn = true
   b. Устанавливает _state.op.manualMode = true   // переход в ручной режим
   c. Вызывает колбэк _stateCallback(&_state, false)  // needSave = false
5. Оркестратор в колбэке:
   a. НЕ вызывает config_save()
   b. Вызывает transport->publish()  // публикация нового состояния
```

## 7. Требования к коду

### 7.1. Стиль

- `snake_case` для функций и переменных
- `PascalCase` для классов и структур
- Doxygen-комментарии для публичных методов
- Файлы начинаются с комментария с названием и назначением

### 7.2. Память

- **Запрещено** динамическое выделение (`new`, `malloc`) в runtime
- Все объекты создаются статически (в main.cpp)
- Использовать `PROGMEM` для строковых констант (HTML, логи)
- Избегать `std::function` (использовать указатели на функции + контекст)

### 7.3. Обработка ошибок

- Все операции с датчиками должны иметь таймауты
- При ошибке датчика — `sensorValid = false`, публикация с `valid = false`
- При ошибке конфигурации — переход в AP-режим
- WDT должен быть включён в production

### 7.4. Логирование

- Критические события → `XLOG_ERROR`
- Переключение режимов → `XLOG_INFO`
- Показания датчика → `XLOG_DEBUG`
- Production: `XLOG_LEVEL = 2` (WARN)

### 7.5. Документирование слоёв

**Принципы оформления документации на слои:**

## 9. Принятые архитектурные решения (резюме)

| Решение | Обоснование |
|---------|-------------|
| **Одна кодовая база** | Исключает дублирование, упрощает поддержку |
| **Оркестратор в main.cpp** | Единая точка сборки, без бизнес-логики |
| **DeviceController — отдельный слой** | Бизнес-логика изолирована от транспорта и инфраструктуры |
| **Config и State разделены** | Постоянные параметры — EEPROM, оперативные — RAM |
| **Постоянные параметры сохраняются немедленно** | Изменения через MQTT/Web записываются в EEPROM сразу |
| **Оперативные параметры не сохраняются** | Только RAM, сбрасываются при перезагрузке |
| **emergency вычисляет Actuator** | Актуатор знает о времени работы |
| **sensorValid вычисляет Sensor** | Датчик знает о валидности данных |
| **Указатели на функции вместо std::function** | Экономия RAM (до 32 байт на колбэк) |
| **Структуры вместо виртуальных методов** | Экономия Flash и RAM |
| **PROGMEM для строк** | Хранение HTML во Flash |
| **Статические объекты** | Экономия RAM, предсказуемость |
| **Web → флаги вместо прямых вызовов** | Web не вызывает `config_save()` и `ESP.restart()` — только устанавливает флаги для оркестратора |
| **Централизованная перезагрузка** | Только `restart_manager.cpp` вызывает `ESP.restart()` |
| **Унифицированный рендеринг Web** | `web_common` предоставляет единые функции рендеринга |
