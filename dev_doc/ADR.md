# Архитектурный базис и контракты компонентов
## (Единая кодовая база для устройств умного дома)

## 1. Введение

### 1.1. Цель документа

Определить неизменяемую архитектуру проекта и правила взаимодействия модулей. Все отклонения от описанных здесь интерфейсов и структуры требуют отдельного согласования.

### 1.2. Назначение и область применения

Настоящий документ описывает архитектуру встраиваемого программного обеспечения для семейства устройств умного дома, объединённых общей кодовой базой. Документ предназначен для команды разработчиков и содержит:

- Принципы построения системы
- Структуру модулей и их ответственность
- Интерфейсы взаимодействия между модулями
- Правила конфигурирования и сборки
- Требования к качеству кода

Документ не содержит описания конкретных алгоритмов работы устройства — это уровень реализации. Здесь описывается **как** система построена, а не **что** она делает в каждом конкретном случае.

## 2. Общие принципы архитектуры

### 2.1. Принцип единой кодовой базы

Проект представляет собой **единый репозиторий**, из которого на этапе компиляции собираются разные бинарные образы для разных типов устройств. Выбор типа устройства и набора функций осуществляется через флаги препроцессора (`-DDEVICE_TYPE`, `-DTRANSPORT_TYPE`).

**Обоснование:**
- Исключает дублирование кода между типами устройств
- Упрощает поддержку — исправление делается один раз
- Снижает риск рассинхронизации между версиями для разных устройств

### 2.2. Принцип разделения ответственности (Single Responsibility)

Каждый модуль отвечает **ровно за одну** функциональную область:

| Модуль | Ответственность |
|--------|-----------------|
| `main.cpp` | Оркестрация — создание и связывание объектов |
| `core/` | Инфраструктура: конфигурация, логирование, LED, WiFi, веб, кнопка сброса |
| `transport/` | Каналы связи: MQTT, Zigbee, Null |
| `sensor/` | Драйверы датчиков: AHT10, DHT22 |
| `device/` | Бизнес-логика для каждого типа устройства |

**Запрещено:**
- Смешивать бизнес-логику с транспортным слоем
- Обращаться к глобальным переменным из модулей (кроме main.cpp)
- Использовать `#ifdef` вне main.cpp за исключением организации заглушек фyнкций или задания дефолтных значений

### 2.3. Принцип инверсии зависимостей (Dependency Inversion)

Модули верхнего уровня (device/) не зависят от модулей нижнего уровня (sensor/, transport/). Зависимости передаются через интерфейсы:

```
device/ → ISensor, ITransport (интерфейсы)
sensor/ → реализует ISensor
transport/ → реализует ITransport
```

**Обоснование:**
- Позволяет подменять реализации (AHT10 ↔ DHT22) без изменения логики
- Упрощает тестирование (можно подставить моки)
- Снижает связанность модулей

### 2.4. Принцип автономности

Устройство **обязано** быть полностью функциональным без внешних каналов связи. Транспорт (MQTT/Zigbee) является надстройкой для мониторинга и удалённого управления, но не основой работы.

**Проверка:** если отключить WiFi и MQTT, устройство продолжает работать по внутренней логике (пороги, таймеры).

### 2.5. Принцип разделения Factory Defaults, Config и State

В системе существуют три уровня хранения параметров:

**Factory Defaults (код):**
- Значения по умолчанию, прописанные в коде или файле `credentials.h`.
- Используются для предзаполнения формы веб-интерфейса при первом запуске.
- НЕ ЗАПИСЫВАЮТСЯ в EEPROM автоматически.

**Config (EEPROM/SPIFFS):**
- Постоянные настройки, задаваемые пользователем через веб-интерфейс.
- Переживают перезагрузку.
- Содержат ВСЕ параметры устройства (включая те, которые могут меняться оперативно — это их значения по умолчанию).
- Изменяются ТОЛЬКО через веб-форму `/save` или аппаратный сброс.

**State (RAM):**
- Текущее оперативное состояние устройства.
- Меняется по командам MQTT/Zigbee или внутренней логике.
- НЕ сохраняется в EEPROM.
- При каждой перезагрузке заново инициализируется из config.

**Правила работы:**

1. **Первый запуск (EEPROM пуст или невалиден):**
   - Устройство загружает Factory Defaults из кода.
   - Переходит в режим настройки (AP + веб-интерфейс).
   - Пользователь через веб-форму заполняет параметры.
   - При сохранении формы Config записывается в EEPROM.

2. **Обычный старт (Config валиден):**
   - Устройство загружает Config из EEPROM.
   - State инициализируется из config.
   - Устройство работает в нормальном режиме.

3. **Команды управления:**
   - Меняют ТОЛЬКО State.
   - Config не изменяется.

4. **Веб-форма `/save`:**
   - Меняет ТОЛЬКО Config (запись в EEPROM).
   - State не изменяется (изменения вступят в силу после перезагрузки).

5. **Аппаратный сброс (кнопка):**
   - Очищает EEPROM (или помечает Config как невалидный).
   - Устройство перезагружается и переходит в режим настройки (см. п.1).

6. **Перезагрузка:**
   - State заново инициализируется из Config (все оперативные изменения теряются).

### 2.6. Принцип разделения Транспорта и Инфраструктуры

**Инфраструктура** — обеспечивает настройку, диагностику и обновление устройства. Работает всегда, когда есть питание. Включает:
- Точку доступа (AP) для первоначальной настройки
- Веб-сервер для настройки, диагностики и OTA
- Кнопку сброса настроек

**Транспорт** — обеспечивает интеграцию с внешними системами (Home Assistant, Яндекс Умный дом). Работает только в нормальном режиме (когда есть валидная конфигурация и установлено соединение). Включает:
- MQTT клиент
- Zigbee стек
- Null транспорт (заглушка для автономного режима)

**Взаимодействие:**
- Инфраструктура и транспорт **параллельны** и не зависят друг от друга.
- Инфраструктура имеет **приоритет** над транспортом.
- Если транспорт потерян — инфраструктура всё ещё работает.
- Если конфигурация повреждена — транспорт не запускается, инфраструктура активна.
