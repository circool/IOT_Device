## 1. Назначение

Документ описывает **единый интерфейс** для всех каналов связи.

**Цель:** Оркестратор работает с транспортом через единый интерфейс `Transport`, не привязываясь к конкретной реализации.

**Транспорт** объединяет:
- **Среду передачи** (WiFi, Zigbee, Thread) — обеспечивает физическое соединение
- **Прикладные протоколы** (MQTT, HTTP, ZCL, Matter) — обеспечивают обмен данными
- **Провизионинг** — первоначальную настройку для доступа к среде

Одна среда может поддерживать **несколько прикладных протоколов** одновременно. Например, WiFi + MQTT + HTTP.

## 2. Принципы

| Принцип | Описание |
|---------|----------|
| **Единый интерфейс** | Все транспорты реализуют структуру `Transport` с одинаковыми методами |
| **Самодостаточность** | Транспорт сам управляет своей средой и провизионингом |
| **Среда и протоколы разделены** | Транспорт управляет средой отдельно от протоколов. Среда может быть общей для нескольких протоколов |
| **Указатели на функции** | Вместо `std::function` — экономия RAM |
| **Контекст** | Каждый колбэк принимает `void* context` для передачи состояния |
| **Компиляция** | Выбор транспорта — через `#if` в `transport_factory.h` |
| **Независимость** | Транспорт не знает о бизнес-логике, только о командах и публикациях |

### 2.1. Взаимодействие с оркестратором

```
┌────────────────────────────────────────────────────────────────────────────┐
│                              ORCHESTRATOR                                  │
│                                                                            │
│  1. Создаёт транспорт через фабрику: transport = createTransport()         │
│  2. Передаёт конфигурацию: transport->begin(config)                        │
│  3. В loop(): transport->update() — всегда                                 │
│  4. Регистрирует колбэки:                                                  │
│     - transport->onCommand(callback)                                       │
│     - transport->onConfigUpdate(callback)                                  │
│  5. Публикует данные: transport->publishState(state)                       │
│  6. Проверяет готовность: if (transport->isConnected()) { ... }            │
│                                                                            │
│  Оркестратор НЕ ЗНАЕТ о:                                                   │
│    - Среде (WiFi/ZigBee/Thread)                                            │
│    - Провизионинге                                                         │
│    - Когда запускать провизионинг                                          │
│    - Когда подключаться к среде                                            │
└────────────────────────────────────────────────────────────────────────────┘
                                    │
                                    │ transport->begin(config)
                                    │ transport->update()
                                    ▼
┌────────────────────────────────────────────────────────────────────────────┐
│                              TRANSPORT                                     │
│                                                                            │
│  ВНУТРЕННЯЯ ЛОГИКА (скрыта от оркестратора):                               │
│                                                                            │
│  1. begin(config):                                                         │
│     - Проверяет config → если нет данных → запускает провизионинг          │
│     - Если есть данные → пытается подключиться к среде                     │
│     - Если среда готова → запускает прикладные протоколы                   │
│                                                                            │
│  2. update():                                                              │
│     - Если провизионинг активен → обрабатывает его                         │
│     - Если нет → поддерживает среду и протоколы                            │
│     - При потере связи → пытается переподключиться                         │
│     - Если не может → перезапускает провизионинг                           │
│                                                                            │
│  3. isConnected():                                                         │
│     - Возвращает true только когда всё готово: среда + протоколы           │
└────────────────────────────────────────────────────────────────────────────┘
```

**Ключевые решения, принимаемые транспортом:**

| Ситуация | Решение транспорта |
|----------|-------------------|
| Нет конфигурации среды | Запустить механизм получения конфигурации (провизионинг) |
| Среда потеряна | Пытаться восстановить соединение; при невозможности — перезапустить механизм получения конфигурации |
| Конфигурация получена | Применить конфигурацию и подключиться к среде |

## 3. Структура Transport

```cpp
typedef struct Transport {
    // ===== УПРАВЛЕНИЕ =====
    bool (*begin)(Client* client, const ConfigData* config);
    void (*update)();
    bool (*isConnected)();
    void (*disconnect)();
    const char* (*getName)();

    // ===== ПУБЛИКАЦИЯ (устройство → сеть) =====
    void (*publishOnline)();
    void (*publishState)(bool on);
    void (*publishSpeed)(int percent);
    void (*publishDelaySec)(int seconds);
    void (*publishMaxOnTime)(uint32_t seconds);
    void (*publishSensorControlMode)(bool enabled);
    
    void (*publishSensor)(float temp, float hum);          // TYPE 1,2
    void (*publishAdaptiveMode)(bool enabled);              // TYPE 1
    void (*publishThresholds)(float lowTemp, float highTemp, 
                              float lowHum, float highHum); // TYPE 1
    void (*publishRSSI)(int rssi);
    void (*publishVersion)(const char* version);
    void (*publishResetReason)(const char* reason);

    // ===== КОЛБЭКИ (сеть → устройство) =====
    // 1. Оперативная команда (state, speed, mode)
    void (*onCommand)(TransportCommand cmd, const TransportCommandData* data, void* context);
    
    // 2. Изменение конфигурации (полная структура)
    void (*onConfigUpdate)(const ConfigData* newConfig, void* context);
} Transport;
```

## 4. Типы колбэков

```cpp
// transport_types.h
typedef void (*TransportCommandCallback)(TransportCommand cmd, const TransportCommandData* data, void* context);
typedef void (*TransportConfigCallback)(const ConfigData* newConfig, void* context);
```

**Структура команды:**

```cpp
typedef enum {
    CMD_STATE,                  // bool — включить/выключить
    CMD_SPEED,                  // int — скорость 0-100%
    CMD_SENSOR_CONTROL_MODE,    // bool — AUTO/MANUAL
    CMD_ADAPTIVE_MODE,          // bool — адаптивный режим
} TransportCommand;

typedef struct {
    TransportCommand type;
    union {
        bool boolVal;
        int intVal;
    } value;
} TransportCommandData;
```

## 5. Фабрика транспортов

**Назначение:** выбор реализации на этапе компиляции.

```cpp
// transport_factory.h
inline Transport* createTransport() {
    #if TRANSPORT_TYPE == TRANSPORT_TYPE_WIFI
        return getWiFiTransport();   // Среда: WiFi
                                     // Протоколы: Web (всегда) + MQTT (опционально)
    #elif TRANSPORT_TYPE == TRANSPORT_TYPE_ZIGBEE
        return getZigbeeTransport(); // Среда: Zigbee
                                     // Протоколы: ZCL
    #elif TRANSPORT_TYPE == TRANSPORT_TYPE_THREAD
        #warning "Thread transport not implemented yet"
        return nullptr;
    #else
        return nullptr;
    #endif
}
```

## 6. Среда передачи

Среда передачи — это физический или логический уровень, обеспечивающий связь.

### 6.1. Ответственность среды

| Функция | Описание |
|---------|----------|
| Подключение | Установка соединения с сетью (WiFi STA, Zigbee mesh, Thread mesh) |
| Мониторинг | Отслеживание состояния соединения |
| Переподключение | Восстановление соединения при потере |
| Провизионинг | Получение учётных данных для доступа к среде |

### 6.2. Среда и протоколы

Среда и прикладные протоколы **независимы**:

- Одна среда может поддерживать несколько протоколов (WiFi → MQTT + HTTP)
- Один протокол может работать поверх разных сред (Matter → WiFi или Thread)

**Транспорт управляет средой и предоставляет её протоколам.**

### 6.3. Внутренние компоненты

| Компонент | Среда | Назначение |
|-----------|-------|------------|
| `WiFiManager` | WiFi | Управление STA-режимом, подключение, мониторинг |
| `ZigbeeStack` | Zigbee | Управление Zigbee-стеком, присоединение к сети |
| `ThreadStack` | Thread | Управление Thread-стеком, присоединение к сети |
| `ProvisioningManager` | Любая | Получение учётных данных для доступа к среде |

## 8. Потоки данных

### 8.1. Команда от транспорта к устройству

```
1. Внешняя система отправляет команду
2. Транспорт парсит команду
3. Транспорт вызывает зарегистрированный колбэк onCommand
4. Оркестратор получает колбэк и вызывает DeviceController
5. DeviceController обрабатывает команду
```

### 8.2. Публикация от устройства к транспорту

```
1. DeviceController изменяет состояние
2. DeviceController вызывает _stateCallback(&_state, needSave)
3. Оркестратор получает колбэк
4. Оркестратор вызывает transport->publishState() (или другую публикацию)
5. Транспорт сериализует и отправляет
```

### 8.3. Публикация состояния при подключении

При успешном подключении к среде умного дома транспорт **обязан** выполнить публикацию полного состояния устройства.

```
1. Транспорт успешно подключился к среде
2. Транспорт запустил прикладной протокол
3. Транспорт вызывает внутренний метод publishAll()
```

Что именно публикуется — определяется спецификацией конкретного протокола (`spec_mqtt.md`, `spec_zigbee.md`, `spec_matter.md`).

### 8.4. Изменение конфигурации от транспорта

```
1. Пользователь изменяет постоянный параметр (порог, таймер, режим)
2. Транспорт получает команду
3. Транспорт формирует новую структуру ConfigData
4. Транспорт вызывает onConfigUpdate(&newConfig, context)
5. Оркестратор:
   a. Сохраняет новую конфигурацию в EEPROM
   b. Информирует о новой конфигурации DeviceController
   c. При необходимости перезагружает устройство
```

## 9. Обработка ошибок

| Сценарий | Действие |
|----------|----------|
| **Транспорт не инициализирован** | `createTransport()` возвращает `nullptr` → оркестратор работает без транспорта |
| **Потеря соединения** | Транспорт пытается переподключиться внутри `update()` |
| **Ошибка публикации** | Транспорт логирует ошибку, но не влияет на работу устройства |
| **Некорректная команда** | Транспорт игнорирует команду и логирует ошибку |
| **Нет конфигурации** | Транспорт запускает провизионинг в `begin()` |
| **Потеря среды в процессе работы** | Транспорт пытается переподключиться; при таймауте — перезапускает провизионинг |

## 10. Требования к новым транспортам

При добавлении нового транспорта:

1. **Реализовать все методы структуры `Transport`**
2. **Реализовать управление средой**
3. **Реализовать провизионинг** (если требуется)
4. **Реализовать публикацию состояния при подключении** (`publishAll()`)
5. **Добавить фабрику в `transport_factory.h`**
6. **Поддерживать колбэки `onCommand` и `onConfigUpdate`**
7. **Не зависеть от бизнес-логики** — только команды и публикации
