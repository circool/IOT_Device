Центральный управляющий слой, который связывает все компоненты системы.

## Оглавление

---

## 1. Назначение

Оркестратор — это **единственный слой**, который:
- Знает обо всех слоях и их порядке
- Инициализирует все слои в правильной последовательности
- Вызывает `update()` всех слоёв в правильной последовательности
- Связывает слои через колбэки и/или флаги
- Принимает решения о старте или остановке слоев

**Архитектурные требования:** 
- Оркестратор **не содержит бизнес-логики** — это ответственность контроллера (например для управления актуатором - `DeviceController`).
- Менеджеры слоев содержат свое состояние приватно - **оркестратор только принимает решение нужно ли запускать тот или иной менеджер** (например, вызвать менеджера провизионинга или менеджера вайфая). 
- Оркестратор всегда инициализирует и вызывает **все слои**, включая неиспользуемые - обязанность слоя предоставить заглушки для всех публичных методов.

## 3. Жизненный цикл

### 3.1. setup() — Инициализация

Порядок инициализации **критически важен**:

| # | Слой | Почему именно здесь |
|---|------|---------------------|
| 1 | **Logger** | Должен быть готов до всех остальных для логирования |
| 2 | **ConfigManager** | Загрузка настроек из EEPROM |
| 3 | **SystemState** | Инициализация битовой маски |
| 4 | **WDT** | Защита от зависаний на этапе инициализации |
| 5 | **Sensor** | Датчик нужен для DeviceController |
| 6 | **Actuator** | Актуатор нужен для DeviceController |
| 7 | **DeviceController** | Бизнес-логика — центральный слой |
| 8 | **Transport** | Создание через фабрику (зависит от TRANSPORT_TYPE) |
| 9 | **Web** | HTTP-сервер (зависит от Transport) |
| 11 | **LED** | Индикация (зависит от SystemState) |
| 12 | **Button** | Кнопка управления |
| 13 | **WiFi** | Запуск подключения или AP |
| 14 | **Provisioning** | Запуск, если нет WiFi конфигурации |
| 15 | **RestartManager** | Подготовка к перезагрузкам |

**Ключевые правила:**
- `init()` — только подготовка структур, **железо не активируется**
- Активация происходит только при вызове `connect()` (STA) или `start()` (AP) //@todo Привести имена методов к общему порядку именования
- Transport создаётся **только** после успешной активации STA /@todo перенести в слой транспорта


### 3.2. loop() — Основной цикл

Порядок вызова `update()` **критически важен**:

| # | Слой | Принцип |
|---|------|---------|
| 1 | **WDT** | Сброс сторожевого таймера (САМЫЙ ПЕРВЫЙ) |
| 2 | **Button** | Обновление состояния кнопки (должно обрабатываться часто) |
| 3 | **WiFiManager** | Обновление состояния STA  |
| 4 | **Реакция на флаги** | Запуск или остановка провизионинга по флагам `STATE_WIFI_OK` & `STATE_PROVISIONING` |
| 5 | **Provisioning** | Обновление состояния AP (если активен) |
| 6 | **Sensor** | Чтение показаний (с интервалом) |
| 7 | **Actuator** | Обновление таймеров (delay, maxOnTime) |
| 8 | **DeviceController** | Бизнес-логика (пороги, режимы) |
| 9 | **Transport** | MQTT/Zigbee (только если STA активен) |
| 10 | **Web** | Обработка HTTP-запросов |
| 11 | **Команды Web** | Обработка флагов `g_webCommandPending`, `g_webConfigPending`, `g_webRestartPending` |
| 12 | **LED** | Определение режима → `led_set_mode()` → `led_update()` |
| 13 | **RestartManager** | Проверка необходимости перезагрузки (САМЫЙ ПОСЛЕДНИЙ) |

**Ключевые правила:**
- Оркестратор получает сигналы от слоя состояния, которым управляют менеджеры слоев
- Проверка сигналов должна выполняться **после** обновления слоя `..._update()`

## 4. Межслойное взаимодействие

### 4.1. Колбэки оркестратора
Оркестратор регистрирует колбэки для слоёв, которым требуется уведомлять его о событиях:

| Слой | Тип колбэка | Назначение |
|------|-------------|------------|
| **DeviceController** | `StateCallback` | Уведомление об изменении состояния (флаг `need_save`) |
| **MQTTManager** | `BoolCallback`, `IntCallback`, `FloatCallback` | Команды от брокера (включить/выключить, скорость, пороги) |
| **Web** | Флаги (`g_web*`) | Команды от пользователя через HTTP |

```cpp
//@todo Нужно реализовать единый контракт для колбеков транспортного слоя (например, для команд полученных от брокера MQTT или от web страницы управления состоянием)
```

**Правила регистрации колбэков:**
- Колбэки регистрируются **после** инициализации всех слоёв
- Колбэки **не должны** содержать бизнес-логику — только вызовы методов соответствующего контроллера
- Обработка колбэков должна быть быстрой (не блокировать loop)


### 4.2. Взаимодействие с слоями

### 4.2.1. SystemState
Оркестратор **только читает** биты `SystemState` для принятия решений - состоянием битов управляют соответствующие менеджепы слоев. 
Подробности см в `SYSTEM_STATE.md`

### 4.2.2. DeviceController

Оркестратор управляет бизнес-логикой:

| Действие | Вызов | Когда |
|----------|-------|-------|
| Инициализация | `deviceController.init(config, actuator)` | Один раз в `setup()` |
| Регистрация колбэка | `deviceController.set_state_callback(callback)` | После `init()` |
| Обновление | `deviceController.update()` | Каждый `loop()` |
| Команды | `deviceController.handle_command(type, value)` | Из колбэков транспорта и Web |

**Колбэк DeviceController:**
```cpp
void onStateChange(const operational_state_t* state, bool need_save) {
    if (need_save) {
        g_configManager.save();  // ← ТОЛЬКО ЗДЕСЬ!
    }
    // Публикация состояния через транспорт
    if (g_transport && g_transport->isConnected()) {
        g_transport->publishState(state->is_on);
    }
}
```

Подробности см. в `DEVICE_CONTROLLER.md`.






### 4.2.5. Button

Оркестратор анализирует состояние кнопки анализируя бит `STATE_BUTTON_PRESSED` у `SystemState` и при необходимости запрашивает у слоя `button_manager` фазу состояния.

| Стадия | Действие |
|--------|----------|
| `STAGE_3S` (удержание >3 сек) | `g_configManager.reset()` → `restart_request(500)` |
| Другие стадии | Только LED-индикация (без действий) |

Подробности см. в `BUTTON_MANAGER.md`.
```
// Обработка нажатия кнопки сброса

...
if ((bits & STATE_BUTTON_PRESSED) && !(bits & STATE_RESTART)) {
    ButtonStage stage = button_get_stage();
    if (stage == STAGE_3S) {
        g_configManager.reset();
        restart_request(500);
    }
}
```

### 4.2.x. LED-индикация

Оркестратор определяет режим LED на основе `SystemState`, и устанавливает нужный режим методом `led_set_mode(enum LedMode)`, периодически вызывает `led_update()`. 

Подробности в `LED_MANAGER.md`.

```cpp
loop(){

  ...
    uint16_t bits = system_state_get_bits();
  ...

      led_set_mode(LED_OFF);
  ...

      led_set_mode(LED_ON);
  }
  led_update();    
}

```

## X. Обработка ошибок и восстановление

| Ситуация | Действие оркестратора |
|----------|----------------------|
| **Потеря WiFi** | Запуск провизионинга через `WIFI_FALLBACK_TIMEOUT_MS` |
| **Сбой ConfigManager** | Сброс настроек, перезагрузка |
| **Аварийное отключение (emergency)** | LED переходит в режим `LED_SLOW_BLINK` |
| **Зависание** | WDT перезагружает устройство |
| **Команда перезагрузки** | `restart_request()` с задержкой |
