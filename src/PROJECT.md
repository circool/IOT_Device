# Универсальное устройство умного дома

## Описание проекта

### Цель создания

Устройство разработано для автоматического управления вытяжной вентиляцией в туалете и ванной комнате. В типовой квартирной разводке вытяжной вентилятор подключён к цепи освещения и включается одновременно со светом, работая всё время пока в помещении горит свет — без учёта реальной потребности в вентиляции. Устройство решает эту проблему: вентилятор включается автоматически только при превышении порогов температуры или влажности, а не при каждом использовании помещения.

## Основные возможности и режимы работы

Прошивка устройства универсальна и на этапе компиляции настраивается на один из трёх типов:

| Тип | Назначение | Ключевые компоненты |
|-----|-----------|---------------------|
| 1 | Вентилятор с датчиком | Датчик температуры/влажности + реле |
| 2 | Автономный датчик | Только датчик температуры/влажности |
| 3 | Управляемый выключатель | Реле, без датчика |

Каждый тип поддерживает различные каналы взаимодействия и набор функций, описанных ниже.

---

### Описание режимов работы и функциональных особенностей

#### Общие для всех типов возможности

**Хранение настроек.** Все параметры конфигурации сохраняются в энергонезависимой памяти устройства и не теряются при отключении питания.

**Светодиодная индикация.** Встроенный светодиод отображает текущий статус: наличие соединения с WiFi и MQTT, режим настройки, аварийное отключение исполнительного механизма.

**Режим настройки** При первом включении (отсутствии настроек) или потере связи с настроенной сетью устройство переходит в режим настройки.
Режим поддерживает одновремненную работу 2 каналов настройки:
- WiFi точка доступа. Устройство создаёт собственную WiFi-сеть. Подключившись к ней, пользователь получает доступ к веб-интерфейсу для ввода параметров WiFi и MQTT и остальных применимых параметров (режимы работы, границы диапазонов температуры/влажности итп).
- BLE-комиссионинг. Для устройств поддерживающих пролокол Bluetooth Low Energy (BLE) доступна установка параметров WiFi. Доступен только если у устройства нет настроек WiFi/пароля или соединиться с настроенной сетью не удалось. 

**Каналы взаимодействия:**
- WiFi — транспорт для MQTT и веб-интерфейса
- BLE — комиссионинг (настройка) для ESP32-C3/C6/H2/S3
- Zigbee — перспективный протокол для ESP32-C6/H2
- Matter — перспективный протокол для ESP32-C6/H2

**Сброс настроек.** Предусмотрена возможность принудительного сброса всех параметров к значениям по умолчанию — по команде через канал взаимодействия или длительным нажатием аппаратной кнопки сброса.

**Обновление прошивки.** Поддерживается обновление «по воздуху» (OTA) через веб-интерфейс, без демонтажа устройства.

**Программный Watch Dog.** Аппаратный сторожевой таймер отслеживает зависания устройства и выполняет автоматическую перезагрузку.

---

#### Для типов 1 и 3 (исполнительное устройство)

**Таймер аварийного отключения.** Принудительно отключает нагрузку, если она проработала непрерывно дольше заданного времени. Служит защитным механизмом, предотвращая бесконечную работу. Настраивается **только при конфигурации устройства**, может быть отключён установкой нулевого значения.

**Начальное состояние при старте.** Определяет поведение реле сразу после подачи питания: включено или выключено. Настраивается **только при конфигурации устройства**.

---

#### Для типа 1 (вентилятор, управляемый датчиком)

Устройство типа 1 поддерживает несколько режимов управления исполнительным механизмом. Режимы выстроены по приоритету: **Ручной режим → Режим управления сенсором/таймером**.

**Ручной режим (наивысший приоритет).** Включается немедленно после получения прямой команды пользователя по любому из каналов взаимодействия (MQTT или веб-интерфейс). В этом режиме показания датчика и таймер отложенного включения игнорируются. Таймер аварийного отключения продолжает работать. Данные датчиков продолжают публиковаться. Режим действует до явной команды возврата в режим управления сенсором или до перезагрузки устройства.

**Режим управления сенсором.** Основной автоматический режим. Исполнительный механизм включается при превышении хотя бы одного из верхних порогов: температуры **или** влажности. Выключение происходит только при одновременном снижении **обоих** показателей ниже нижних порогов. Пороги задаются при конфигурации устройства, но могут быть изменены пользователем оперативно (изменения действуют до выключения устройства).

**Режим управления таймером.** Предназначен для ситуаций, когда показания датчика малоинформативны (например, длительное использование туалета без значительных изменений влажности). Исполнительный механизм включается по прошествии заданного периода после подачи питания. Настраивается **только при конфигурации устройства**, может быть отключён установкой нулевого значения.

**Дополнительные возможности для типа 1:**

**Тихий режим (Slow Mode).** Снижает шум вентилятора за счёт импульсной подачи питания (ШИМ) с настраиваемой скважностью 0–100%. Может быть активирован при конфигурации устройства. Пользователь может оперативно включать/выключать этот режим и изменять скважность (изменения действуют до выключения устройства).

**Адаптивный тихий режим.** Работает только при активном тихом режиме. Автоматически увеличивает мощность вентилятора при ухудшении показателей окружающей среды (рост температуры или влажности), чтобы ускорить нормализацию микроклимата. Алгоритм адаптации задаётся жёстко при компиляции. Активируется при конфигурации устройства, пользователь может отключить адаптацию оперативно (изменения действуют до выключения устройства).

---

#### Для типа 2 (автономный датчик)

Устройство выполняет единственную функцию — периодический опрос датчика температуры и влажности и публикацию показаний по доступным каналам взаимодействия. Режимы управления исполнительным механизмом отсутствуют.

---

#### Для типа 3 (управляемый выключатель)

Устройство управляется только прямыми командами пользователя через каналы взаимодействия (ручной режим). Датчик отсутствует, режим управления сенсором и адаптивный тихий режим не применимы.

Доступные функции:
- **Режим управления таймером** — включение по прошествии заданного периода после подачи питания.
- **Таймер аварийного отключения** — принудительное отключение при превышении времени непрерывной работы.

---

## Технические описания и пояснения логики работы

### Логика работы

Устройство работает в двух режимах: **режим настройки** и **обычный режим**.

#### Первый запуск

При включении устройство пытается прочитать конфигурацию из энергонезависимой памяти:
- если параметры корректны — переход в **обычный режим**;
- если параметры отсутствуют или повреждены — переход в **режим настройки**.

#### Режим настройки (APBLE-комиссионинг)

1. Используются значения по умолчанию из `credentials.h`.
2. Запускается точка доступа (AP) с идентификатором вида `{fan|sensor|switch}_XXXX`, где `XXXX` — последние 4 символа MAC-адреса. Эта-же строка используется как `prefix` для MQTT-топиков.
3. Запускается веб-сервер на `192.168.4.1` со страницей настройки.
4. Пользователь вводит (при необходимости изменяет) параметры WiFi и MQTT и сохраняет их.
5. После сохранения устройство перезагружается и переходит в **обычный режим**.

Перед сохранением введённых пользователем настроек производится их валидация. В режиме настройки опрос датчиков и управление исполнительным механизмом не производятся.

### Режим настройки (BLE-комиссионинг)

#### Совместимые приложения
Для настройки устройства используется приложение **ESP BLE Prov** от Espressif. 
После успешного получения настроек WiFi BLE-комиссионинг отключается - остальные настройки производятся на web-странице настройки 

#### Обычный режим

1. Чтение конфигурации из энергонезависимой памяти.
2. Инициализация датчика (если предусмотрен типом устройства).
3. Инициализация пина управления исполнительным механизмом (если предусмотрен).
4. Запуск основной логики, **не дожидаясь** подключения к каналам взаимодействия:
   - периодический опрос датчика;
   - управление исполнительным механизмом согласно приоритету режимов;
   - контроль таймера аварийного отключения;
   - обслуживание веб-сервера.
5. Подключение к WiFi-сети по сохранённым параметрам.
6. При невозможности подключения в течение заданного тайм-аута — переход в **режим настройки**.
7. Подключение к MQTT-брокеру, публикация статуса `Online`.
8. При потере соединения — автоматические попытки переподключения.
9. Устройство поднимает веб-сервер отображающий страницу состояния (опцилгально) и страницу настройки параметров. Также веб-сервер поддерживает станицу обновления прошивки по воздуху (опционально)

---

### Описание режимов и терминов

**Ручной режим.** Активируется внешней командой по каналам взаимодействия. Блокирует управление от датчика и таймера. Возврат — командой `sensorControlMode` или перезагрузкой.

**Режим управления таймером.** Включение нагрузки по истечении `delaySeconds` после подачи питания. Работает **параллельно** с режимом управления сенсором (если включен): таймер может включить вентилятор независимо от показаний датчика, однако срабатывание таймера переводит управление в ручной режим, игнорирующий показания сенсора. Отключается командой ручного управления.

**Состояние исполнительного механизма при старте.** Параметр, определяющий положение реле сразу после подачи питания: включено/выключено. Настраивается при конфигурации.

**Тихий режим (Slow Mode).** ШИМ-управление с настраиваемой скважностью 0–100%. Стартовый импульс на полной мощности обеспечивает надёжный пуск вентилятора. Значения ниже минимального порога интерпретируются как команда выключения.

**Адаптивный тихий режим.** При активном тихом режиме отслеживает изменение показателей среды и динамически увеличивает скважность. При ошибке датчика переключает вентилятор на полную мощность. Ручное изменение скважности отключает адаптацию.

**Сохранение и отображение настроек.** Постоянные параметры сохраняются только через веб-форму конфигурации. Оперативные изменения действуют до перезагрузки и не сохраняются в энергонезависимой памяти.

**Принудительный сброс настроек.** Выполняется длительным нажатием кнопки сброса, командой MQTT или через веб-интерфейс. Устройство перезагружается в режим настройки.

**Программный Watch Dog.** Аппаратный таймер, перезагружающий устройство при зависании.

**Отображение причины перезагрузки.** При перезагрузке по ошибке причина публикуется в MQTT-топик `{prefix}/last_reset`. Штатные перезагрузки не публикуются.

**Индикация состояния соединений.** Светодиод отображает факт срабатывания таймера аварийного отключения, режим точки доступа, текущий статус подключения к WiFi и MQTT: постоянное свечение — работа в штатном режиме, серии вспышек — нештатное состояние.

### Состояние системы

Устройство использует единое состояние `SystemState` — источник правды для всех слоёв:

| Состояние | LED режим |
|-----------|-----------|
| `INIT` | Выключен |
| `NORMAL` | Постоянно горит |
| `MODE_1` | 1 вспышка/сек |
| `MODE_2` | 2 вспышки/сек |
| `MODE_3` | 3 вспышки/сек |
| `MODE_4` | Медленное мигание |
| `RESTART_PENDING` | Выключен |

Состояние обновляется через `system_state_set()` и логируется автоматически.

## Техническая информация

### Индикация состояния соединений

Устройство использует светодиод для отображения текущего статуса. Индикация работает, если в конфигурации задан пин светодиода (`STATUS_LED_PIN`). При значении `0` функция отключена.

Управление LED:
- `led_init()` — инициализация пина
- `led_update()` — обновление физического состояния (мигание)
- **Не содержит логики** — читает `g_systemState`

| Состояние | Сигнал светодиода |
|-----------|-------------------|
| Подключение к WiFi и MQTT установлено | Постоянное свечение |
| Потеря соединения с WiFi | Одиночные вспышки с интервалом 1 сек |
| Потеря соединения с MQTT (WiFi активен) | Двойные вспышки с интервалом 1 сек |
| Режим настройки (точка доступа AP) | Тройные вспышки с интервалом 1 сек |
| Режим настройки (BLE-комиссионинг) | Тройные вспышки с интервалом 1 сек |
| Аварийное отключение исполнительного механизма | Вспышки длиной 1 сек интервалом 2 сек |

### Каналы взаимодействия — описание и особенности

#### MQTT

MQTT — основной протокол интеграции устройства в экосистемы умного дома. Устройство подключается к заданному брокеру, публикует своё состояние и принимает команды управления.

**Принцип формирования топиков**

Все топики строятся по схеме: `{prefix}/{группа}/{параметр}`

Префикс (`prefix`) формируется при первом запуске на основе типа устройства и последних четырёх символов MAC-адреса:
- `fan_XXXX` — для типа 1 (вентилятор с датчиком)
- `sensor_XXXX` — для типа 2 (автономный датчик)
- `switch_XXXX` — для типа 3 (управляемый выключатель)

Топики управления (команды от брокера к устройству) формируются добавлением `c/` в путь: `{prefix}/c/{группа}/{параметр}`

---

**Топики только для публикации (устройство → брокер)**

Устройство публикует значения, управление извне не предусмотрено.

| Топик | Описание | Применимость |
|-------|----------|--------------|
| `{prefix}/status` | Статус устройства: `Online` / `Offline` (LWT) | Все типы |
| `{prefix}/sensor/temperature` | Текущая температура | Типы 1, 2 |
| `{prefix}/sensor/humidity` | Текущая влажность | Типы 1, 2 |
| `{prefix}/last_reset` | Причина последней перезагрузки | Все типы  |
| `{prefix}/version` | Версия прошивки | Все типы |
| `{prefix}/rssi` | Сила сигнала WiFi | Все типы |

---

**Топики только для управления (брокер → устройство)**

Устройство принимает команды, но не публикует текущее значение параметра.

| Топик | Описание | Применимость |
|-------|----------|--------------|
| `{prefix}/c/system/reset` | Сброс настроек к значениям по умолчанию | Все типы |

---

**Двунаправленные топики (публикация и управление)**

Устройство публикует текущее значение параметра и принимает команды на его изменение.

*Исполнительное устройство (типы 1, 3):*

| Топик | Описание | Применимость |
|-------|----------|--------------|
| `{prefix}/fan/state` | Состояние исполнительного механизма | Типы 1, 3 |
| `{prefix}/fan/delaySec` | Задержка отложенного включения | Типы 1, 3 |
| `{prefix}/fan/maxOnTime` | Время аварийного отключения | Типы 1, 3 |

**Примечание:** для типа 3 (выключатель) в топиках используется `switch` вместо `fan`.

*Режимы работы (только тип 1):*

| Топик | Описание |
|-------|----------|
| `{prefix}/fan/sensorControlMode` | Режим управления сенсором |
| `{prefix}/fan/adaptiveMode` | Адаптивный тихий режим |
| `{prefix}/fan/speed` | Текущая скважность ШИМ |

*Пороги датчика (только тип 1):*

| Топик | Описание |
|-------|----------|
| `{prefix}/sensor/lowTemp` | Нижний порог температуры |
| `{prefix}/sensor/highTemp` | Верхний порог температуры |
| `{prefix}/sensor/lowHum` | Нижний порог влажности |
| `{prefix}/sensor/highHum` | Верхний порог влажности |

---

**Особенности взаимодействия:**
- Прямая команда управления состоянием автоматически переводит устройство в ручной режим.
- Все команды имеют оперативный характер — действуют до перезагрузки устройства.
- Сохранение параметров в энергонезависимую память производится **только** через веб-интерфейс.
- При выключении исполнительного механизма скважность ШИМ восстанавливается до сохранённого значения.
- При ручном изменении скважности адаптивный режим автоматически отключается.

### Режимы отладки и логирования

## Описание слоев

### settings.h
Конфигуратор констант и их валидатор. Устанавливает правильные зависимости между слоями.

### system_state.h/cpp
**Состояние системы.** Единый источник правды для всех слоёв. Логирует изменения через `CAT_SYSTEM`.

### restart_manager.h/cpp
**Менеджер перезагрузок.** Централизованное управление перезагрузкой. Защита от повторных запросов, задержка перед `ESP.restart()`.

### config_manager.h/cpp
**Менеджер настроек.** Хранит значения в EEPROM, управляет загрузкой/сохранением, валидацией параметров.

### logger.h/cpp
**Система логирования.** Вывод в Serial с фильтрацией по уровню и категориям. Поддерживает цветной вывод.

### led.h/cpp
**Светодиодная индикация.** Простой исполнитель — читает `g_systemState` и отображает соответствующий режим.

### wdt_manager.h/cpp
**Watchdog таймер.** Аппаратный сторожевой таймер, защищающий от зависаний.

### reset_btn.h/cpp
**Кнопка сброса.** Обработка нажатий с определением длительности (PRESSED, STAGE_1S, STAGE_2S, STAGE_3S).

### sensor.h/cpp
**Датчик температуры и влажности.** Чтение с AHT10 (I2C) или DHT11/DHT22.

### actuator_base.h/cpp
**Базовый класс исполнительного механизма.** Управление реле, таймеры.

### fan_actuator.h/cpp
**Управление вентилятором (тип 1).** ШИМ, адаптивный режим, стартовый импульс.

### switch_actuator.h/cpp
**Управление выключателем (тип 3).** Простое включение/выключение реле.

### wifi_manager.h/cpp
**WiFi-подключение.** STA и AP режимы, мониторинг, fallback.

### mqtt.h/cpp
**MQTT-клиент.** Подключение к брокеру, публикация, приём команд.

### web.h/cpp
**Веб-интерфейс.** HTTP-сервер для управления и настройки.

### ota.h/cpp
**OTA-обновления.** Обновление прошивки через веб-интерфейс.

### provisioning.h/cpp
**Менеджер комиссионинга.** Управление BLE и AP настройкой.

### ble_server.h/cpp
**BLE-сервер.** ESP BLE Provisioning для ESP32.

### main.cpp
**Оркестратор.** Точка входа. Инициализирует все слои, вызывает их в loop. Единственный, кто вызывает `ConfigManager::save()` и `ESP.restart()`.

## Предстоит исправить

| **Нарушение** | **Почему** | **Степень** |
|--------------|-----------|-------------|
| **Бизнес-логика в `main.cpp`** | Оркестратор должен только связывать, а не принимать решения. Сейчас `main.cpp` содержит логику управления вентилятором на основе датчика. | Средняя |
| **Актуаторы читают ConfigManager напрямую** | Бизнес-слой знает об инфраструктуре. | ⚠️ Средняя |
| **Web знает о `apMode`** | В текущем коде Web управляет AP режимом. | Высокая (будет исправлено) |
| **Web вызывает `ESP.restart()`** | Перезагрузка — ответственность оркестратора. | Высокая (будет исправлено) |
| **Web вызывает `ConfigManager::save()`** | Сохранение — ответственность оркестратора. | Высокая (будет исправлено) |
| **Нет `IWebStatusProvider` интерфейса** | Web зависит от конкретных классов, а не от абстракции. | Средняя (есть в плане) |

## Предстоит исправить

| **Нарушение** | **Почему** | **Степень** |
|--------------|-----------|-------------|
| **Бизнес-логика в `main.cpp`** | Оркестратор должен только связывать, а не принимать решения. | Средняя |
| **Актуаторы читают ConfigManager напрямую** | Бизнес-слой знает об инфраструктуре. | ⚠️ Средняя |
| **Web знает о `apMode`** | В текущем коде Web управляет AP режимом. | Высокая |
| **Web вызывает `ESP.restart()`** | Перезагрузка — ответственность оркестратора. | Высокая |
| **Web вызывает `ConfigManager::save()`** | Сохранение — ответственность оркестратора. | Высокая |
| **Нет `IWebStatusProvider` интерфейса** | Web зависит от конкретных классов. | Средняя |

## Реализованная архитектура (текущее состояние)

На данный момент реализована базовая инфраструктура с чётким разделением ответственности:

### 1. Единое состояние системы (`system_state`)

**Назначение:** единственный источник правды для всех слоёв.

**Реализация:**
- `enum class SystemState` — состояния системы
- `g_systemState` — глобальная переменная состояния
- `system_state_set()` — установка состояния с автоматическим логированием
- `system_state_get()` — чтение текущего состояния

**Состояния:**
- `INIT` — инициализация (LED выключен)
- `NORMAL` — нормальная работа (LED горит)
- `MODE_1` — нет WiFi / кнопка 0-1с (1 вспышка)
- `MODE_2` — нет MQTT / кнопка 1-2с (2 вспышки)
- `MODE_3` — Provisioning / кнопка 2-3с (3 вспышки)
- `MODE_4` — аварийное отключение (медленное мигание)
- `RESTART_PENDING` — ожидание перезагрузки (LED выключен)

**Принцип работы:**
```
Каждый слой → system_state_set() → g_systemState → LED читает → отображает
                     ↓
              автоматический лог
```

---

### 2. Менеджер перезагрузок (`restart_manager`)

**Назначение:** централизованное управление перезагрузкой устройства.

**Реализация:**
- `restart_request(delayMs)` — запрос перезагрузки с задержкой
- `restart_loop()` — проверка в loop(), выполнение `ESP.restart()`
- Защита от повторных запросов (флаг `_pending`)
- Логирование через `CAT_RESTART`

**Принцип работы:**
```
Любой слой → restart_request(500) → _pending = true → _time = now + 500ms
                                                          ↓
                                              restart_loop() в loop()
                                                          ↓
                                              ESP.restart()
```

**Используется:**
- Кнопкой сброса (после сброса конфигурации)
- OTA обновлением
- Другими слоями при необходимости

---

### 3. LED индикация (`led`)

**Назначение:** отображение состояния системы.

**Реализация:**
- `led_init()` — инициализация пина
- `led_update()` — чтение `g_systemState` и обновление физического состояния
- **Не содержит логики** — только отображение
- Использует `millis()` для неблокирующего мигания

**Принцип работы:**
```
g_systemState → led_update() → switch → shouldBeOn → digitalWrite()
```

---

### 4. Оркестратор (`main.cpp`)

**Назначение:** точка входа, инициализация и координация всех слоёв.

**Реализация:**
- `setup()` — инициализация всех слоёв, установка `INIT`
- `loop()` — последовательный вызов всех слоёв в правильном порядке

**Порядок в `loop()`:**
1. `wdt_feed()` — кормление Watchdog
2. Обработка кнопки сброса — обновление состояния
3. Обновление состояния от других слоёв (заглушки)
4. `led_update()` — отображение состояния
5. `restart_loop()` — проверка перезагрузки

**Принцип работы:**
```
setup() → инициализация всех слоёв → g_systemState = INIT
loop() → каждый слой обновляет g_systemState → LED отображает → Restart проверяет
```

### 6. Ключевые принципы

1. **Единый источник правды** — все слои читают/пишут `g_systemState`
2. **Автоматическое логирование** — все изменения состояния логируются
3. **Централизованная перезагрузка** — единая точка вызова `ESP.restart()`
4. **Разделение ответственности** — каждый слой делает только своё
5. **Асинхронность** — все слои используют `millis()`, нет блокирующих задержек
