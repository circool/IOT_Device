# Универсальное устройство умного дома

## Описание проекта

### Цель создания

Устройство разработано для автоматического управления вытяжной вентиляцией в туалете и ванной комнате. В типовой квартирной разводке вытяжной вентилятор подключён к цепи освещения и включается одновременно со светом, работая всё время пока в помещении горит свет — без учёта реальной потребности в вентиляции. Устройство решает эту проблему: вентилятор включается автоматически только при превышении порогов температуры или влажности, а не при каждом использовании помещения.

## Основные возможности и режимы работы

Прошивка устройства универсальна и на этапе компиляции настраивается на один из трёх типов:

| Тип | Назначение | Ключевые компоненты |
|-----|-----------|---------------------|
| 1 | Вентилятор с датчиком | Датчик температуры/влажности + реле |
| 2 | Автономный датчик | Только датчик температуры/влажности |
| 3 | Управляемый выключатель | Реле, без датчика |

Каждый тип поддерживает различные каналы взаимодействия и набор функций, описанных ниже.

---

### Описание режимов работы и функциональных особенностей

#### Общие для всех типов возможности

**Хранение настроек.** Все параметры конфигурации сохраняются в энергонезависимой памяти устройства и не теряются при отключении питания.

**Светодиодная индикация.** Встроенный светодиод отображает текущий статус: наличие соединения с WiFi и MQTT, режим настройки, аварийное отключение исполнительного механизма.

**Режим настройки** При первом включении (отсутствии настроек) или потере связи с настроенной сетью устройство переходит в режим настройки.
Режим поддерживает одновремненную работу 2 каналов настройки:
- WiFi точка доступа. Устройство создаёт собственную WiFi-сеть. Подключившись к ней, пользователь получает доступ к веб-интерфейсу для ввода параметров WiFi и MQTT и остальных применимых параметров (режимы работы, границы диапазонов температуры/влажности итп).
- BLE-комиссионинг. Для устройств поддерживающих пролокол Bluetooth Low Energy (BLE) доступна установка параметров WiFi. Доступен только если у устройства нет настроек WiFi/пароля или соединиться с настроенной сетью не удалось. 


**Каналы взаимодействия:**
- WiFi — транспорт для MQTT и веб-интерфейса
- BLE — комиссионинг (настройка) для ESP32-C3/C6/H2/S3
- Zigbee — перспективный протокол для ESP32-C6/H2
- Matter — перспективный протокол для ESP32-C6/H2

**Сброс настроек.** Предусмотрена возможность принудительного сброса всех параметров к значениям по умолчанию — по команде через канал взаимодействия или длительным нажатием аппаратной кнопки сброса.

**Обновление прошивки.** Поддерживается обновление «по воздуху» (OTA) через веб-интерфейс, без демонтажа устройства.

**Программный Watch Dog.** Аппаратный сторожевой таймер отслеживает зависания устройства и выполняет автоматическую перезагрузку.

---

#### Для типов 1 и 3 (исполнительное устройство)

**Таймер аварийного отключения.** Принудительно отключает нагрузку, если она проработала непрерывно дольше заданного времени. Служит защитным механизмом, предотвращая бесконечную работу. Настраивается **только при конфигурации устройства**, может быть отключён установкой нулевого значения.

**Начальное состояние при старте.** Определяет поведение реле сразу после подачи питания: включено или выключено. Настраивается **только при конфигурации устройства**.

---

#### Для типа 1 (вентилятор, управляемый датчиком)

Устройство типа 1 поддерживает несколько режимов управления исполнительным механизмом. Режимы выстроены по приоритету: **Ручной режим → Режим управления сенсором/таймером**.

**Ручной режим (наивысший приоритет).** Включается немедленно после получения прямой команды пользователя по любому из каналов взаимодействия (MQTT или веб-интерфейс). В этом режиме показания датчика и таймер отложенного включения игнорируются. Таймер аварийного отключения продолжает работать. Данные датчиков продолжают публиковаться. Режим действует до явной команды возврата в режим управления сенсором или до перезагрузки устройства.

**Режим управления сенсором.** Основной автоматический режим. Исполнительный механизм включается при превышении хотя бы одного из верхних порогов: температуры **или** влажности. Выключение происходит только при одновременном снижении **обоих** показателей ниже нижних порогов. Пороги задаются при конфигурации устройства, но могут быть изменены пользователем оперативно (изменения действуют до выключения устройства).

**Режим управления таймером.** Предназначен для ситуаций, когда показания датчика малоинформативны (например, длительное использование туалета без значительных изменений влажности). Исполнительный механизм включается по прошествии заданного периода после подачи питания. Настраивается **только при конфигурации устройства**, может быть отключён установкой нулевого значения.

**Дополнительные возможности для типа 1:**

**Тихий режим (Slow Mode).** Снижает шум вентилятора за счёт импульсной подачи питания (ШИМ) с настраиваемой скважностью 0–100%. Может быть активирован при конфигурации устройства. Пользователь может оперативно включать/выключать этот режим и изменять скважность (изменения действуют до выключения устройства).

**Адаптивный тихий режим.** Работает только при активном тихом режиме. Автоматически увеличивает мощность вентилятора при ухудшении показателей окружающей среды (рост температуры или влажности), чтобы ускорить нормализацию микроклимата. Алгоритм адаптации задаётся жёстко при компиляции. Активируется при конфигурации устройства, пользователь может отключить адаптацию оперативно (изменения действуют до выключения устройства).

---

#### Для типа 2 (автономный датчик)

Устройство выполняет единственную функцию — периодический опрос датчика температуры и влажности и публикацию показаний по доступным каналам взаимодействия. Режимы управления исполнительным механизмом отсутствуют.

---

#### Для типа 3 (управляемый выключатель)

Устройство управляется только прямыми командами пользователя через каналы взаимодействия (ручной режим). Датчик отсутствует, режим управления сенсором и адаптивный тихий режим не применимы.

Доступные функции:
- **Режим управления таймером** — включение по прошествии заданного периода после подачи питания.
- **Таймер аварийного отключения** — принудительное отключение при превышении времени непрерывной работы.

---

## Технические описания и пояснения логики работы

### Логика работы

Устройство работает в двух режимах: **режим настройки** и **обычный режим**.

#### Первый запуск

При включении устройство пытается прочитать конфигурацию из энергонезависимой памяти:
- если параметры корректны — переход в **обычный режим**;
- если параметры отсутствуют или повреждены — переход в **режим настройки**.

#### Режим настройки (APBLE-комиссионинг)

1. Используются значения по умолчанию из `credentials.h`.
2. Запускается точка доступа (AP) с идентификатором вида `{fan|sensor|switch}_XXXX`, где `XXXX` — последние 4 символа MAC-адреса. Эта-же строка используется как `prefix` для MQTT-топиков.
3. Запускается веб-сервер на `192.168.4.1` со страницей настройки.
4. Пользователь вводит (при необходимости изменяет) параметры WiFi и MQTT и сохраняет их.
5. После сохранения устройство перезагружается и переходит в **обычный режим**.

Перед сохранением введённых пользователем настроек производится их валидация. В режиме настройки опрос датчиков и управление исполнительным механизмом не производятся.

### Режим настройки (BLE-комиссионинг)

#### Совместимые приложения
Для настройки устройства используется приложение **ESP BLE Prov** от Espressif. 
После успешного получения настроек WiFi BLE-комиссионинг отключается - остальные настройки производятся на web-странице настройки 

#### Обычный режим

1. Чтение конфигурации из энергонезависимой памяти.
2. Инициализация датчика (если предусмотрен типом устройства).
3. Инициализация пина управления исполнительным механизмом (если предусмотрен).
4. Запуск основной логики, **не дожидаясь** подключения к каналам взаимодействия:
   - периодический опрос датчика;
   - управление исполнительным механизмом согласно приоритету режимов;
   - контроль таймера аварийного отключения;
   - обслуживание веб-сервера.
5. Подключение к WiFi-сети по сохранённым параметрам.
6. При невозможности подключения в течение заданного тайм-аута — переход в **режим настройки**.
7. Подключение к MQTT-брокеру, публикация статуса `Online`.
8. При потере соединения — автоматические попытки переподключения.
9. Устройство поднимает веб-сервер отображающий страницу состояния (опцилгально) и страницу настройки параметров. Также веб-сервер поддерживает станицу обновления прошивки по воздуху (опционально)

---

### Описание режимов и терминов

**Ручной режим.** Активируется внешней командой по каналам взаимодействия. Блокирует управление от датчика и таймера. Возврат — командой `sensorControlMode` или перезагрузкой.

**Режим управления таймером.** Включение нагрузки по истечении `delaySeconds` после подачи питания. Работает **параллельно** с режимом управления сенсором (если включен): таймер может включить вентилятор независимо от показаний датчика, однако срабатывание таймера переводит управление в ручной режим, игнорирующий показания сенсора. Отключается командой ручного управления.

**Состояние исполнительного механизма при старте.** Параметр, определяющий положение реле сразу после подачи питания: включено/выключено. Настраивается при конфигурации.

**Тихий режим (Slow Mode).** ШИМ-управление с настраиваемой скважностью 0–100%. Стартовый импульс на полной мощности обеспечивает надёжный пуск вентилятора. Значения ниже минимального порога интерпретируются как команда выключения.

**Адаптивный тихий режим.** При активном тихом режиме отслеживает изменение показателей среды и динамически увеличивает скважность. При ошибке датчика переключает вентилятор на полную мощность. Ручное изменение скважности отключает адаптацию.

**Сохранение и отображение настроек.** Постоянные параметры сохраняются только через веб-форму конфигурации. Оперативные изменения действуют до перезагрузки и не сохраняются в энергонезависимой памяти.

**Принудительный сброс настроек.** Выполняется длительным нажатием кнопки сброса, командой MQTT или через веб-интерфейс. Устройство перезагружается в режим настройки.

**Программный Watch Dog.** Аппаратный таймер, перезагружающий устройство при зависании.

**Отображение причины перезагрузки.** При перезагрузке по ошибке причина публикуется в MQTT-топик `{prefix}/last_reset`. Штатные перезагрузки не публикуются.

**Индикация состояния соединений.** Светодиод отображает факт срабатывания таймера аварийного отключения, режим точки доступа, текущий статус подключения к WiFi и MQTT: постоянное свечение — работа в штатном режиме, серии вспышек — нештатное состояние.

## Техническая информация

### Индикация состояния соединений

Устройство использует светодиод для отображения текущего статуса подключения. Индикация работает, если в конфигурации задан пин светодиода (`STATUS_LED_PIN`). При значении `0` функция отключена.
Для отладки удобно использовать имеющийся на мекетных платах синий светодиод (на 2 пине). 
Для нестандартного подключения предусмотрена возможность инверсии логики (константа `LED_INVERTED`)

| Состояние | Сигнал светодиода |
|-----------|-------------------|
| Подключение к WiFi и MQTT установлено | Постоянное свечение |
| Потеря соединения с WiFi | Одиночные вспышки с интервалом 1 сек |
| Потеря соединения с MQTT (WiFi активен) | Двойные вспышки с интервалом 1 сек |
| Режим настройки (точка доступа AP) | Тройные вспышки с интервалом 1 сек |
| Режим настройки (BLE-комиссионинг) | Тройные вспышки с интервалом 1 сек |
| Аварийное отключение исполнительного механизма | Вспышки длиной 1 сек интервалом 2 сек |

**Примечание:** Визуально AP и BLE-режимы индицируются одинаково (тройные вспышки), так как оба являются режимами настройки. В логах можно различить по сообщениям `Mode: SETUP (AP)` или `Mode: SETUP (BLE)`.

Индикация позволяет быстро диагностировать состояние устройства без доступа к веб-интерфейсу или MQTT.

### Каналы взаимодействия — описание и особенности

#### MQTT

MQTT — основной протокол интеграции устройства в экосистемы умного дома. Устройство подключается к заданному брокеру, публикует своё состояние и принимает команды управления.

**Принцип формирования топиков**

Все топики строятся по схеме: `{prefix}/{группа}/{параметр}`

Префикс (`prefix`) формируется при первом запуске на основе типа устройства и последних четырёх символов MAC-адреса:
- `fan_XXXX` — для типа 1 (вентилятор с датчиком)
- `sensor_XXXX` — для типа 2 (автономный датчик)
- `switch_XXXX` — для типа 3 (управляемый выключатель)

Топики управления (команды от брокера к устройству) формируются добавлением `c/` в путь: `{prefix}/c/{группа}/{параметр}`

---

**Топики только для публикации (устройство → брокер)**

Устройство публикует значения, управление извне не предусмотрено.

| Топик | Описание | Применимость |
|-------|----------|--------------|
| `{prefix}/status` | Статус устройства: `Online` / `Offline` (LWT) | Все типы |
| `{prefix}/sensor/temperature` | Текущая температура | Типы 1, 2 |
| `{prefix}/sensor/humidity` | Текущая влажность | Типы 1, 2 |
| `{prefix}/last_reset` | Причина последней перезагрузки | Все типы  |
| `{prefix}/version` | Версия прошивки | Все типы |
| `{prefix}/rssi` | Сила сигнала WiFi | Все типы |

---

**Топики только для управления (брокер → устройство)**

Устройство принимает команды, но не публикует текущее значение параметра.

| Топик | Описание | Применимость |
|-------|----------|--------------|
| `{prefix}/c/system/reset` | Сброс настроек к значениям по умолчанию | Все типы |

---

**Двунаправленные топики (публикация и управление)**

Устройство публикует текущее значение параметра и принимает команды на его изменение.

*Исполнительное устройство (типы 1, 3):*

| Топик | Описание | Применимость |
|-------|----------|--------------|
| `{prefix}/fan/state` | Состояние исполнительного механизма | Типы 1, 3 |
| `{prefix}/fan/delaySec` | Задержка отложенного включения | Типы 1, 3 |
| `{prefix}/fan/maxOnTime` | Время аварийного отключения | Типы 1, 3 |

**Примечание:** для типа 3 (выключатель) в топиках используется `switch` вместо `fan`.

*Режимы работы (только тип 1):*

| Топик | Описание |
|-------|----------|
| `{prefix}/fan/sensorControlMode` | Режим управления сенсором |
| `{prefix}/fan/adaptiveMode` | Адаптивный тихий режим |
| `{prefix}/fan/speed` | Текущая скважность ШИМ |

*Пороги датчика (только тип 1):*

| Топик | Описание |
|-------|----------|
| `{prefix}/sensor/lowTemp` | Нижний порог температуры |
| `{prefix}/sensor/highTemp` | Верхний порог температуры |
| `{prefix}/sensor/lowHum` | Нижний порог влажности |
| `{prefix}/sensor/highHum` | Верхний порог влажности |

---

**Особенности взаимодействия:**
- Прямая команда управления состоянием автоматически переводит устройство в ручной режим.
- Все команды имеют оперативный характер — действуют до перезагрузки устройства.
- Сохранение параметров в энергонезависимую память производится **только** через веб-интерфейс.
- При выключении исполнительного механизма скважность ШИМ восстанавливается до сохранённого значения.
- При ручном изменении скважности адаптивный режим автоматически отключается.

### Режимы отладки и логирования

#### Уровни логирования

Уровень логирования задаётся макросом `XLOG_LEVEL` в `config.h` или через `build_flags` в `platformio.ini`:

| Значение | Уровень | Описание |
|----------|---------|----------|
| 0 | NONE | Логирование отключено полностью |
| 1 | ERROR | Только критические ошибки |
| 2 | WARN | Предупреждения + ERROR |
| 3 | INFO | Основные события (подключение, переключение режимов) + WARN + ERROR |
| 4 | DEBUG | Все сообщения, включая отладочные (по умолчанию) |

**Пример установки в `platformio.ini`:**
```ini
build_flags =
    -DXLOG_LEVEL=3    ; INFO уровень
```

#### Категории логирования

Категории позволяют фильтровать сообщения по модулям. Значение `XLOG_CATEGORIES` — битовая маска.

| Категория | Бит | Значение | Описание |
|-----------|-----|----------|----------|
| CAT_CONFIG | 1 << 0 | 1 | Конфигурация и EEPROM |
| CAT_SENSOR | 1 << 1 | 2 | Датчик температуры/влажности |
| CAT_FAN | 1 << 2 | 4 | Вентилятор (управление, ШИМ) |
| CAT_SWITCH | 1 << 3 | 8 | Выключатель |
| CAT_ACTUATOR | 1 << 4 | 16 | Базовый класс исполнительного механизма |
| CAT_MQTT | 1 << 5 | 32 | MQTT-клиент (подключение, публикации) |
| CAT_WIFI | 1 << 6 | 64 | WiFi (подключение, AP режим) |
| CAT_WEB | 1 << 7 | 128 | Web-сервер |
| CAT_OTA | 1 << 8 | 256 | OTA обновления |
| CAT_LED | 1 << 9 | 512 | Светодиодная индикация |
| CAT_WDT | 1 << 10 | 1024 | Watchdog таймер |
| CAT_AP | 1 << 11 | 2048 | Режим точки доступа |
| CAT_MAIN | 1 << 12 | 4096 | Основной цикл и инициализация |
| CAT_PROVISIONING | 1 << 13 | 8192 | BLE-комиссионинг |

**Комбинации категорий:**

| Значение | Включённые категории |
|----------|---------------------|
| `0xFFFF` | Все категории (по умолчанию) |
| `0x0001` | Только CAT_CONFIG |
| `0x0060` | CAT_MQTT + CAT_WIFI (32+64) |
| `0x0FFF` | Все категории, кроме CAT_MAIN |
| `0x2000` | Только CAT_PROVISIONING |

**Пример включения только WiFi и MQTT логов:**
```ini
build_flags =
    -DXLOG_CATEGORIES=0x0060
```

#### Цветной вывод

Цветной вывод логов в терминал включён по умолчанию (`XLOG_USE_COLOR = 1`). Уровни имеют следующие цвета:

| Уровень | Цвет |
|---------|------|
| ERROR | Ярко-красный |
| WARN | Ярко-пурпурный |
| INFO | Стандартный (сброс) |
| DEBUG | Синий |

**Отключение цветов:**
```ini
build_flags =
    -DXLOG_USE_COLOR=0
```

#### Примеры настройки в `platformio.ini`

```ini
[common]
build_flags =
    ; Только ошибки и предупреждения, без отладочных сообщений
    -DXLOG_LEVEL=2
    
    ; Только MQTT и WiFi логи
    -DXLOG_CATEGORIES=0x0060
    
    ; Монохромный вывод (без ANSI-цветов)
    -DXLOG_USE_COLOR=0
```

#### Логирование в коде

Для добавления логов в прошивку используются макросы:

```cpp
XLOG_ERROR(CAT_MODULE, "Ошибка: %s", reason);
XLOG_WARN(CAT_MODULE, "Предупреждение: %d", value);
XLOG_INFO(CAT_MODULE, "Событие выполнено");
XLOG_DEBUG(CAT_MODULE, "Отладочная информация: %.2f", data);
```

Где `CAT_MODULE` — одна из категорий из таблицы выше.

#### Особенности

- Логи выводятся в последовательный порт (`Serial`) со скоростью `MONITOR_SPEED` (по умолчанию 115200)
- При включённом цветном выводе логгер автоматически сбрасывает цвет перед каждой строкой для корректного отображения в терминалах
- Сообщения длиннее 256 символов обрезаются
- При уровне `XLOG_LEVEL_NONE (0)` все макросы логирования превращаются в пустые операции, не потребляя ресурсы

## BLE-Provisioning
Поднимается BLE комиссионинг
BLE-комиссионинг — метод первоначальной настройки WiFi на устройстве с использованием Bluetooth Low Energy. Реализован на базе протокола **ESP BLE Provisioning** от Espressif.

- Заводские настройки (`credentials.h`)

### Zigbee (перспективный протокол)

#### Обзор

Zigbee — протокол для построения ячеистых сетей с низким энергопотреблением. Устройство подключается к координатору сети (например, Zigbee-шлюзу) и представляет себя как одно или несколько логических устройств (endpoints) со стандартизированными кластерами.

**Поддерживаемые платформы:**
- ESP32-C6 (поддержка Zigbee в ESP-IDF)
- ESP32-H2 (поддержка Zigbee в ESP-IDF)

**Текущий статус:** Проектирование, базовая архитектура реализована в виде заглушек.

#### Принцип адресации

Устройство идентифицируется в сети по 16-битному сетевому адресу и 64-битному MAC-адресу. Взаимодействие строится по модели:
`{endpoint} → {cluster} → {attribute}`

#### Конечные точки (Endpoints)

Устройство представляет три конечные точки в зависимости от конфигурации типа:

| Endpoint | Назначение | Применимость |
|----------|------------|--------------|
| 1 | Управление вентилятором | Типы 1, 3 |
| 2 | Датчик температуры и влажности | Типы 1, 2 |
| 3 | Конфигурация устройства | Все типы |

#### Кластеры и атрибуты

*Endpoint 1 — Управление вентилятором (типы 1, 3):*

| Кластер | Тип | Атрибуты |
|---------|-----|----------|
| On/Off (0x0006) | Сервер | `OnOff` — состояние исполнительного механизма |
| Level Control (0x0008) | Сервер | `CurrentLevel` — скважность ШИМ (0–100%) |
| Fan Control (0x0202) | Сервер | `FanMode` — режим работы (ручной/сенсор); `FanModeSequence` — адаптивный режим |

*Endpoint 2 — Датчик (типы 1, 2):*

| Кластер | Тип | Атрибуты |
|---------|-----|----------|
| Temperature Measurement (0x0402) | Сервер | `MeasuredValue` — текущая температура |
| Relative Humidity Measurement (0x0405) | Сервер | `MeasuredValue` — текущая влажность |

*Endpoint 3 — Конфигурация (все типы):*

| Кластер | Тип | Атрибуты |
|---------|-----|----------|
| Basic (0x0000) | Сервер | `ManufacturerName`, `ModelIdentifier`, `SWBuildID` — информация об устройстве и версии прошивки |
| OTA Upgrade (0x0019) | Клиент | Обновление прошивки по воздуху |
| Custom (0xFC00) | Сервер | Пороги датчика (`LowTemp`, `HighTemp`, `LowHum`, `HighHum`); таймеры (`DelaySeconds`, `MaxOnTime`); причина перезагрузки |

#### Типы взаимодействия

| Кластер | Публикация | Управление |
|---------|-----------|------------|
| On/Off | Да. Состояние сообщается через `Report Attributes` | Да. Команды `On`, `Off`, `Toggle` |
| Level Control | Да. Текущий уровень | Да. Команда `MoveToLevel` |
| Fan Control | Да. Текущий режим | Да. Команда `Write Attributes` |
| Temperature Measurement | Да. Периодические отчёты | Нет |
| Relative Humidity Measurement | Да. Периодические отчёты | Нет |
| Basic | Да. Статические атрибуты | Нет |
| OTA Upgrade | Нет | Да. Приём обновлений |
| Custom | Да. Текущие значения | Да. `Write Attributes` для порогов и таймеров |

**Особенности:**
- Обмен данными происходит через механизм биндингов (прямые связи между устройствами) или через координатор.
- Периодичность отчётов датчиков настраивается через конфигурацию кластеров.
- При потере и восстановлении связи устройство автоматически перерегистрируется в сети.

### Matter (перспективный протокол)

#### Обзор

Matter — современный протокол умного дома, работающий поверх IP (WiFi, Thread). Обеспечивает унифицированное представление устройства и взаимодействие с экосистемами разных производителей.

**Поддерживаемые платформы:**
- ESP32-C6 (поддержка Matter в ESP-IDF)
- ESP32-H2 (поддержка Matter в ESP-IDF)

**Текущий статус:** Проектирование.

#### Принцип представления

Устройство представляется как единый Matter-узел (Node), содержащий несколько конечных точек (Endpoints) с типами устройств и кластерами, описанными в спецификации Matter. Взаимодействие строится по модели:
`{Node ID} → {Endpoint} → {Cluster} → {Attribute}`

#### Типы устройств (Device Types)

Каждая конечная точка соответствует стандартизированному типу устройства:

| Endpoint | Device Type | Применимость |
|----------|-------------|--------------|
| 0 | Aggregator (0x000E) | Все типы (корневая точка) |
| 1 | Extended Color Light (0x010D) | Типы 1, 3 |
| 2 | Temperature Sensor (0x0302) | Типы 1, 2 |
| 3 | Humidity Sensor (0x0307) | Типы 1, 2 |

**Примечание:** Extended Color Light используется вместо Fan, так как спецификация Matter на момент написания не включает отдельный тип для вентилятора. Управление скоростью реализуется через атрибут `CurrentLevel`.

#### Кластеры и атрибуты

*Endpoint 1 — Extended Color Light (типы 1, 3):*

| Кластер | Обязательность | Атрибуты и команды |
|---------|---------------|---------------------|
| Identify (0x0003) | Обязательный | `Identify` — визуальная идентификация устройства |
| On/Off (0x0006) | Обязательный | `OnOff` — состояние; команды `On`, `Off`, `Toggle` |
| Level Control (0x0008) | Обязательный | `CurrentLevel` — скважность ШИМ; команда `MoveToLevel` |
| Groups (0x0004) | Обязательный | Групповое управление |

*Endpoint 2 — Temperature Sensor (типы 1, 2):*

| Кластер | Обязательность | Атрибуты |
|---------|---------------|----------|
| Temperature Measurement (0x0402) | Обязательный | `MeasuredValue` — текущая температура |

*Endpoint 3 — Humidity Sensor (типы 1, 2):*

| Кластер | Обязательность | Атрибуты |
|---------|---------------|----------|
| Relative Humidity Measurement (0x0405) | Обязательный | `MeasuredValue` — текущая влажность |

*Общие кластеры (все конечные точки):*

| Кластер | Назначение |
|---------|------------|
| Descriptor (0x001D) | Идентификация типа устройства и состава конечной точки |
| Basic Information (0x0028) | `VendorName`, `ProductName`, `SoftwareVersion`, причина перезагрузки |
| OTA Software Update (0x002A) | Обновление прошивки по воздуху |

*Пользовательские параметры:*

Пороги датчика, таймеры и настройки режимов вынесены в пользовательский кластер на Endpoint 0 (Aggregator):

| Кластер | Атрибуты |
|---------|----------|
| Custom (0xFC00) | `SensorControlMode`, `AdaptiveMode`, `LowTemp`, `HighTemp`, `LowHum`, `HighHum`, `DelaySeconds`, `MaxOnTime` |

#### Типы взаимодействия

| Кластер | Публикация | Управление |
|---------|-----------|------------|
| On/Off | Да. Подписка на атрибут `OnOff` | Да. Команды `On`, `Off`, `Toggle` |
| Level Control | Да. Подписка на атрибут `CurrentLevel` | Да. Команда `MoveToLevel` |
| Temperature Measurement | Да. Подписка на атрибут | Нет |
| Relative Humidity Measurement | Да. Подписка на атрибут | Нет |
| Basic Information | Да. Статические атрибуты | Нет |
| OTA Software Update | Нет | Да. Приём обновлений |
| Custom | Да. Подписка на атрибуты | Да. `WriteAttribute` |

**Особенности:**
- Matter использует модель «подписок» (subscriptions) вместо периодической публикации: контроллер подписывается на атрибуты и получает обновления при их изменении.
- Устройство поддерживает multi-admin: одновременную работу с несколькими экосистемами (Apple Home, Google Home, Amazon Alexa и др.).
- Настройка выполняется через стандартную процедуру комиссионинга (commissioning) с QR-кодом или числовым кодом.
- OTA-обновления инициируются со стороны Matter-контроллера.

### WEB-интерфейс

WEB-интерфейс предоставляет прямой доступ к настройке и управлению устройством через браузер. Доступен по HTTP.

**Режимы доступа:**

| Режим | Адрес | Условия доступа |
|-------|-------|-----------------|
| Обычный режим | IP-адрес устройства в локальной сети | Устройство подключено к WiFi |
| Режим настройки (AP) | `192.168.4.1` | Устройство в режиме точки доступа |

**Страницы веб-интерфейса:**

| Страница | Назначение | Особенности |
|----------|------------|-------------|
| `/` | Страница состояния | Текущие показания датчиков, статус исполнительного механизма, активные режимы, оставшееся время до аварийного отключения |
| `/config` | Страница настройки | Форма изменения параметров WiFi, MQTT, порогов датчиков, таймеров |
| `/save` | Сохранение настроек | Принимает POST-запрос из формы `/config`, сохраняет параметры в EEPROM, перезагружает устройство |
| `/update` | OTA-обновление | Загрузка файла прошивки, автоматическая перезагрузка после обновления |

**Особенности:**
- Только изменения, сохранённые через `/config` → `/save`, записываются в энергонезависимую память.
- Оперативные команды (включение/выключение, смена режима, изменение скважности) действуют до перезагрузки.
- OTA-обновление является единственным способом обновления прошивки без демонтажа устройства.

**WiFi:**

Конфигуратор констант и их валидатор. Устанавливает правильные зависимости между слоями и задает значения констант по умолчанию.

#### Полная таблица ключей `settings.h`

| Ключ | Условие | Дефолт |
|------|---------|--------|

| | `DEVICE_TYPE == 2` | `"sensor"` |
| | `DEVICE_TYPE == 3` | `"switch"` |
| `TRANSPORT_TYPE` | `CONFIG_IDF_TARGET_ESP32C6` или `CONFIG_IDF_TARGET_ESP32H2` | `1` (ZigBee) |
| | Остальные платформы | `0` (MQTT) |
| `PROVISIONING_METHOD` | `ESP8266` | `2` (AP) |
| | Остальные платформы | `3` (BLE+AP) |
| | `TRANSPORT_TYPE == 1` (ZigBee) | `0` (Нет) |

#### Проверки зависимостей (выполняются на этапе препроцессора)

| Проверка | Условие | Действие |
|----------|---------|----------|
| **OTA требует WEB** | `FEATURE_OTA_ENABLED == 1 && FEATURE_WEB_ENABLED == 0` | `#error` |
| **WEB требует WiFi** | `FEATURE_WEB_ENABLED == 1 && FEATURE_WIFI_ENABLED == 0` | `#error` |
| **TYPE 1 требует датчик** | `DEVICE_TYPE == 1 && FEATURE_SENSOR_ENABLED == 0` | `#error` |
| **TYPE 2 требует датчик** | `DEVICE_TYPE == 2 && FEATURE_SENSOR_ENABLED == 0` | `#error` |
| **TYPE 3 не требует датчик** | `DEVICE_TYPE == 3 && FEATURE_SENSOR_ENABLED == 1` | `#warning` + принудительное отключение |
| **TRANSPORT_TYPE валидность** | `< 0 или > 2` | `#error` |
| **ZigBee требует C6/H2** | `TRANSPORT_TYPE == 1` без `CONFIG_IDF_TARGET_ESP32C6/H2` | `#error` |
| **ZigBee отключает WiFi** | `TRANSPORT_TYPE == 1 && FEATURE_WIFI_ENABLED == 1` | `#warning` + принудительное отключение |
| **ZigBee отключает Provisioning** | `TRANSPORT_TYPE == 1` | `#warning` + принудительная установка `PROVISIONING_METHOD=0` |
| **ZigBee отключает WEB** | `TRANSPORT_TYPE == 1 && FEATURE_WEB_ENABLED == 1` | `#warning` + принудительное отключение |
| **ZigBee отключает OTA** | `TRANSPORT_TYPE == 1 && FEATURE_OTA_ENABLED == 1` | `#warning` + принудительное отключение |
| **Matter экспериментальный** | `TRANSPORT_TYPE == 2` без C6/H2 | `#warning` |
| **ESP8266 не поддерживает BLE** | `PROVISIONING_METHOD == 1/3 && ESP8266` | `#warning` + принудительная установка `PROVISIONING_METHOD=2` |
| **PROVISIONING_METHOD валидность** | `< 0 или > 3` | `#warning` + принудительная установка `0` |
| **DEVICE_TYPE валидность** | `< 1 или > 3` | `#error` |

### config_manager.h/cpp

**Менеджер настроек и конфигурации.** Хранит значения в EEPROM, управляет загрузкой/сохранением, валидацией параметров и дефолтными значениями. Загружает заводские настройки из `credentials.h`.

**Определяет:** `TEMP_MIN/MAX`, `HUM_MIN/MAX`, `SENSOR_INTERVAL_MIN/MAX`, `DELAY_SECONDS_MIN/MAX`, `MAX_ON_TIME_MIN/MAX`, все `DEFAULT_*`, `MAGIC_VALUE`, `EEPROM_SIZE`, креденшелы из `credentials.h`

---

### logger.h/cpp

**Система логирования.** Вывод отладочной информации в Serial с фильтрацией по уровню (NONE/ERROR/WARN/INFO/DEBUG) и категориям (модулям). Поддерживает цветной вывод.

**Определяет:** `XLOG_LEVEL`, `XLOG_CATEGORIES`, `XLOG_USE_COLOR`, `MONITOR_SPEED`

---

### led.h/cpp

**Светодиодная индикация.** Отображает статус устройства: подключение к WiFi/MQTT, режим настройки, аварийное отключение.

**Определяет:** `STATUS_LED_PIN`, `LED_INVERTED`

---

### sensor.h/cpp

**Датчик температуры и влажности.** Чтение показаний с AHT10 (I2C) или DHT11/DHT22 (GPIO). Возвращает температуру, влажность, скорость изменения влажности и статус ошибки.

**Определяет:** `SENSOR_TYPE`, `I2C_SDA_PIN`, `I2C_SCL_PIN`, `SENSOR_PIN`

---

### actuator_base.h/cpp

**Базовый класс исполнительного механизма.** Управление реле/вентилятором: включение/выключение, таймер отложенного включения, таймер аварийного отключения. Используется как основа для `FanActuator` и `SwitchActuator`.

**Определяет:** `SWITCH_PIN`, `RELAY_ON_LEVEL`

---

### fan_actuator.h/cpp

**Управление вентилятором (тип 1).** ШИМ-управление скоростью, адаптивный тихий режим, стартовый импульс для надежного запуска. Наследует `ActuatorBase`.

**Определяет:** `PWM_FREQUENCY`, `PWM_RESOLUTION`, `PWM_STARTING`, `ADAPTIVE_STEP_SIZE`, `ADAPTIVE_SPEED_SENSITIVITY`, `ADAPTIVE_EPSILON_TEMP`, `ADAPTIVE_EPSILON_HUM`

---

### switch_actuator.h/cpp

**Управление выключателем (тип 3).** Простое включение/выключение реле без ШИМ. Наследует `ActuatorBase`.

---

### wifi_manager.h/cpp

**WiFi-подключение.** Управление подключением к WiFi сети (STA-режим), запуск точки доступа (AP-режим) для настройки, мониторинг соединения, fallback в AP при потере связи.

**Определяет:** `WIFI_CONNECT_TIMEOUT_MS`, `AP_FALLBACK_TIMEOUT_MS`

---

### mqtt.h/cpp

**MQTT-клиент.** Подключение к брокеру, публикация состояния и показаний датчиков, прием команд управления. Формирует топики на основе префикса устройства.

**Определяет:** `MQTT_PORT`, `MQTT_PUBLISH_RSSI`, `MQTT_PUBLISH_VERSION`, `MQTT_PUBLISH_RESET_REASON`, `MQTT_RESET_ENABLED`, `MQTT_IGNORE_PUBLISH_NORMAL_RESET_REASONS`, `STATE_PUBLISH_INTERVAL_MS`, `MQTT_RECONNECT_DELAY_MS`, `MQTT_KEEPALIVE_SEC`

---

### zigbee.h/cpp

**ZigBee-протокол (перспективный).** Реализация ZigBee-стека для ESP32-C6/H2. Представляет устройство как конечные точки с кластерами On/Off, Level Control, Temperature/Humidity Measurement.

---

### provisioning.h/cpp

**Менеджер комиссионинга.** Управляет процессом первоначальной настройки устройства. Выбирает метод (BLE/AP) на основе `PROVISIONING_METHOD`, собирает данные от обоих каналов, передает их в оркестратор через колбэк.

**Определяет:** `BLE_PROVISIONING_PIN`, `BLE_DEVICE_NAME`, `AP_IP_ADDRESS`, `USE_BLE_PROVISIONING`, `USE_AP_PROVISIONING` (производные от `PROVISIONING_METHOD`)

---

### ble_server.h/cpp

**BLE-сервер провизионинга.** Реализует ESP BLE Provisioning для ESP32. Принимает WiFi SSID и пароль через приложение ESP BLE Prov, передает данные в `ProvisioningManager` через колбэк.

---

### web.h/cpp

**Веб-интерфейс.** HTTP-сервер для управления и настройки устройства. Страницы: состояние (`/`), настройки (`/config`), OTA-обновление (`/update`). Работает в STA-режиме (обычный) и AP-режиме (настройка).

**Определяет:** `WEB_STATUS_ENABLED`, `WEB_SHOW_RSSI`, `WEB_RESET_ENABLED`, `DEFAULT_WEB_REFRESH`, `WEB_SERVER_TIMEOUT_MS`

---

### ota.h/cpp

**OTA-обновления.** Обновление прошивки "по воздуху" через веб-интерфейс (`/update`). Использует библиотеку ElegantOTA. Требует минимум 2MB Flash.

**Определяет:** `OTA_PORT` (если нужен)

---

### wdt_manager.h/cpp

**Watchdog таймер.** Аппаратный сторожевой таймер, защищающий от зависаний. Автоматически перезагружает устройство при сбое. Таймаут настраивается через `WDT_TIMER_MS`.

**Определяет:** `WDT_TIMER_MS`

---

### reset_btn.h
**Определяет:** `RESET_PIN` (дефолт для кнопки сброса)

### main.cpp

**Оркестратор.** Точка входа в программу. Единственный, кто знает о всех модулях. Получает данные через колбэки от транспортов, управляет LED, переключает режимы (настройка/нормальный), вызывает `.update()` и `.loop()` всех модулей. ## Предстоит исправить

| **Нарушение** | **Почему** | **Степень** |
|--------------|-----------|-------------|
| **Бизнес-логика в `main.cpp`** | Оркестратор должен только связывать, а не принимать решения. Сейчас `main.cpp` содержит логику управления вентилятором на основе датчика. В планах вынести все слои | Средняя |
| **Актуаторы читают ConfigManager напрямую** | Бизнес-слой знает об инфраструктуре. `FanActuator` вызывает `g_configManager.getXXX()` | ⚠️ Средняя |
| **Web знает о `apMode`** | В текущем коде Web управляет AP режимом | Высокая (будет исправлено) |
| **Web вызывает `ESP.restart()`** | Перезагрузка — ответственность оркестратора | Высокая (будет исправлено) |
| **Web вызывает `ConfigManager::save()`** | Сохранение — ответственность оркестратора | Высокая (будет исправлено) |
| **Нет `IWebStatusProvider` интерфейса** | Web зависит от конкретных классов (FanActuator, MQTTManager), а не от абстракции | Средняя (есть в плане) |
